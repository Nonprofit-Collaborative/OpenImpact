# G-07 and G-11 integration notes

What the integrator has to add to files this feature does not own: permission sets,
layouts, and the record page. Everything else in commitments is self contained.

Feature: commitments (pledges and recurring gifts) and the commitment rollup definitions.
Branch: `feature/g-07-g-11-commitments`.

## Permission set entries

No permission set file is edited by this branch. Add these to the Giving permission sets
(the user set for David and Jen, the admin set for Maria).

### Object permissions

| Object | User set | Admin set |
|---|---|---|
| `Commitment__c` | Read, Create, Edit | Read, Create, Edit, Delete, View All |
| `Installment__c` | Read, Create, Edit | Read, Create, Edit, Delete, View All |

Delete is deliberately not granted to the user set: a commitment or a payment that has
been paid cannot be deleted at all, and an unpaid one is cancelled or skipped rather than
removed.

## Layout placements

This branch adds no field to a layout it does not own.

1. **Gift layout** (owned by the Giving objects feature): add `Commitment__c` and
   `Installment__c` next to `Appeal__c` in the gift's main section, in that order.
   Installment is the more specific of the two, so it reads better second.
2. **Commitment record page** (Lightning app builder, shipped as a FlexiPage by whoever
   ships the Giving app): put the `commitmentSchedulePreview` component in the main
   column under the details, and the Installments related list below it. The component
   carries the "Generate now" action for a commitment whose schedule is missing.
3. **Installment record page**: the shipped page layout is enough; no component.
4. **Giving Settings console section** (owned by the settings console feature): the three
   admin-editable commitment settings arrive through `Setting_Definition__mdt` rows in
   section Giving, so nothing is hand placed. `Installment_Top_Up_Last_Run__c` has no
   definition row on purpose: it is written by the job and shown on the Hub, not edited.

## Module turn-on

Turning the Giving module on must call `GivingScheduler.scheduleAll()`. It schedules the
two daily jobs (installment top up at 01:15, overdue pass at 01:45) and is safe to call
twice: a job already scheduled under the same name is left alone and the failure is
logged, not thrown.

## Contract assumptions to verify at integration

These were written against the contracts in the brief, with no org to check them in.

1. **`TriggerHandler` shape: verified against Core.** The handlers extend `TriggerHandler`
   and override no argument methods (`beforeInsert`, `beforeUpdate`, `beforeDelete`,
   `afterInsert`, `afterUpdate`), reading the records through `newRecords()`,
   `oldRecords()`, and `oldRecordsById()` as the base class requires, and passing them to
   `@TestVisible` methods that take explicit lists.
2. **`ErrorLogger.log(Exception thrown, String context)`: verified against Core.** The
   argument order is exception first.
3. **`SettingsService.getValue(String settingsObject, String key)` returns `Object`:
   verified against Core.** It is the raw field value, so a Number setting arrives as a
   `Decimal` and a Checkbox setting as a `Boolean`. `CommitmentService` accepts both those
   and a text form, and falls back to the documented default when the value is null or
   unparseable.
4. **`HouseholdService.getHouseholdIdsFor(Set<Id>)` returns `Map<Id, Id>`**, person
   identifier to household account identifier, and accepts both contact and account
   identifiers.
5. **Custom metadata field API names: verified against Core.** `Automation_Registry__mdt`
   is `Description__c`, `Enabled_By_Default__c`, `Handler_Class__c`, `Object_Name__c`,
   `Execution_Order__c`. `Setting_Definition__mdt` is `Setting_Key__c` (the settings
   field's API name), `Settings_Object__c`, `Section__c`, `Module__c`, `Data_Type__c`,
   `Description__c`, `Help_Path__c`, `Sort_Order__c`. There is no `Default_Value__c` on
   `Setting_Definition__mdt`, so each setting's default lives in the field metadata that
   the Giving objects feature owns and in the constants in `CommitmentService`.
6. **Possible duplicate setting definitions.** This branch ships
   `Setting_Definition.Installment_Generation_Horizon_Months` and
   `Setting_Definition.Installment_Overdue_Grace_Days` because the commitments feature is
   what those settings are for. The Giving objects feature owns the two fields themselves
   on `Giving_Settings__c`. If it also ships definition rows with these developer names,
   keep one copy of each and delete the other.
7. **Gift fields read by this feature:** `Amount__c`, `Status__c` (value `Received`),
   `Gift_Date__c`, `Donor_Contact__c`, `Commitment__c`, `Installment__c`.

## Known limits, deliberately

- The top up runs as a batch (`InstallmentTopUpBatch`) over every active recurring
  commitment, twenty five per chunk, so an org of any size has every schedule extended.
  It is a batch and not a single pass on purpose: a thousand weekly commitments imply more
  expected payments than one transaction may insert, and the capped single query this
  feature started with would have extended the same oldest commitments every night and
  never reached the rest.
- The overdue pass considers at most 5,000 payments per run and queries only payments that
  are still Scheduled. Rows already marked Overdue are outside the query on purpose: they
  already carry the right status, and including them would let a backlog fill the cap every
  night so a newly overdue payment was never reached. A backlog larger than 5,000 therefore
  drains at 5,000 a night rather than starving.
- `Balance__c` is a formula, so the pledge balance rollups aggregate a formula field. This
  is what canonical model R-CM5 specifies, and it is a requirement on the aggregation
  engine adapter (ADR-0015). If the engine cannot aggregate a formula, R-CM5 already says
  what to do instead: store Balance from the domain layer, and record the reason.

  `packages/giving`, so the three rollups that target it have their field waiting for them.
