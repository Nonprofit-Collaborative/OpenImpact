# G-03 and G-06: permission and integration requests

Permission sets are integrated centrally (plan Section 9.2: shared metadata belongs to one
integrating agent), so this branch ships no permission set. This file is the request.

## Permission set entries

Target sets: the packaged permission set groups named in plan Section 4.8. Where a group is
not built yet, the entries belong on the set that will sit inside it.

### Nonprofit Admin and Fundraising Staff

| Kind | Entry | Access |
|---|---|---|
| Apex class | `QuickGiftEntryController` | Enabled |
| Tab | `Quick_Gift_Entry` | Visible |
| Tab | `Gift__c`, `Fund__c`, `Appeal__c` | Visible |
| Application | `Fundraising` | Visible |
| Object | `Gift__c` | Read, Create, Edit |
| Object | `Gift_Allocation__c` | Read, Create, Edit |
| Object | `Fund__c` | Read |
| Object | `Appeal__c` | Read |
| Field | `Gift__c.Donor_Contact__c`, `Donor_Account__c`, `Gift_Date__c`, `Amount__c`, `Type__c`, `Status__c`, `Appeal__c`, `Payment_Reference__c` | Read, Edit |
| Field | `Gift_Allocation__c.Gift__c`, `Fund__c`, `Amount__c` | Read, Edit |
| Field | `Fund__c.Active__c`, `Appeal__c.Active__c` | Read |

The controller runs every query and every DML in user mode, so a missing field permission
shows as a save failure rather than as silently dropped data. That is deliberate, and it
makes these entries load bearing.

### Read Only (Tom and board users)

| Kind | Entry | Access |
|---|---|---|
| Application | `Fundraising` | Visible |
| Tab | `Gift__c`, `Fund__c`, `Appeal__c` | Visible |
| Object | `Gift__c`, `Gift_Allocation__c`, `Fund__c`, `Appeal__c` | Read |
| Field | every field listed above | Read |

Read Only users do not need `QuickGiftEntryController` or the Quick Gift Entry tab.

### Custom permission

`Enter_Gifts` (plan Section 7.1) is not checked by this feature: access to Quick Gift Entry
is object access plus tab visibility, which is what an administrator expects to manage. If
the integrator adds `Enter_Gifts` to the model, it belongs on Nonprofit Admin and
Fundraising Staff, and the controller can start checking it without a schema change.

## Folder access, which is not permission set metadata

The packaged folders `Open Impact Giving` (reports) and `Open Impact Giving` (dashboards)
ship with public access set to read only. Everyone who can read gifts can read them; editing
them needs the standard "Manage Reports in Public Folders" and "Manage Dashboards in Public
Folders" user permissions, which belong on Nonprofit Admin. Please add those two user
permissions to that set.

## Requests to other packages

1. **Core, C-03 Hub home page: a Modules tile.** ADR-0018 puts each module's tabs in its own
   Lightning app, because a package cannot add a tab to another package's app. The Hub home
   page should list the module apps that are installed, each as a link that opens the app, so
   that Maria and Tom cross between the Hub and Fundraising without the app launcher. Giving
   ships no record for this: detection is the same describe based check the Module Manager
   already makes.
2. **Nothing from the Setup Assistant.** An earlier draft of this file asked C-12 for a step
   setting the dashboard's running user. It is not needed: `Giving_Overview` ships with
   `dashboardType` set to `LoggedInUser`, so it reads as whoever opens it and arrives working.
   Neither feature has a post-install action beyond the permission entries above.

## Known gaps for the integrator

1. **Closed.** *No test runs as a non-administrator.* `GivingUserModeTest` now assigns
   `Nonprofit_Admin` plus `Giving_Admin`, `Nonprofit_Staff` plus `Giving_Staff`, and
   `Nonprofit_Read_Only` plus `Giving_Read_Only` inside `System.runAs`, and proves that quick
   gift entry, a refund, a tribute notification, and a commitment pause all work for the first
   two and are refused with a readable message for the third. The Core set is assigned alongside
   the Giving set because a Giving set alone carries no access to the people the gifts are from,
   which is how the shipped permission set groups pair them.
2. **Closed at merge.** *Three fields the package writes in user mode were not editable in any
   Giving set.* Found by writing the test above. They are now editable on `Giving_Admin` and
   `Giving_Staff` and read only on `Giving_Read_Only`, exactly as requested below. The two
   tests that were waiting on it can now be written.

   | Field | Written by | Effect today |
   |---|---|---|
   | `Gift__c.Tribute__c` | `TributeService.mirrorOnGifts`, after insert and after delete on `Tribute__c`, `AccessLevel.USER_MODE` | A staff or admin user who adds a tribute to a gift has the save refused |
   | `Soft_Credit__c.Is_Automatic__c` | `SoftCreditController.addCredit` (sets it false) and `SoftCreditService` (sets it true for automatic household credits), both `AccessLevel.USER_MODE` | A staff or admin user who adds a soft credit, or who saves a gift for a donor with other household members, has the save refused |
   | `Soft_Credit__c.Percent__c` | `SoftCreditService`, when it inserts or updates automatic credits, `AccessLevel.USER_MODE` | The same |

   Both sets currently carry these three as readable and not editable, which is right for what a
   person may type and wrong for what the package writes. Please make them editable on
   `Giving_Admin` and `Giving_Staff` and leave them read only on `Giving_Read_Only`. Note that
   `Gift__c.Household__c` and `Commitment__c.Household__c` are in the same shape but need no
   change: they are written in before triggers, where the running user's field level security
   has already been applied to the record as submitted.

   Two tests wait on this: a staff user adding a soft credit, and a staff user adding a tribute.
   `GivingUserModeTest` says so where they belong.
3. **A gift saved with no default fund anywhere is refused,** not saved without an allocation
   (`GiftService.applyDefaultAllocations` adds `Giving_Gift_DefaultFundMissing` to the gift).
   The admin guide pages say so. If G-01 ever softens that to a warning, both pages change.
