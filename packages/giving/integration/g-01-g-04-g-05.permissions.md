# G-01, G-04, G-05: permissions and integration notes

This feature ships no permission set files. The Giving package's three permission sets are
assembled once, by the agent that owns them, so that three feature branches do not each
rewrite the same XML. This page is the input that feature G-01 (gifts, allocations, funds),
G-04 (refunds and write-offs) and G-05 (appeals) hand over.

Objects, fields, tabs and classes below are all in this feature's metadata, under
`packages/giving/main/default`.

## Giving_Admin

Maria configures giving and fixes mistakes.

| Kind | Entry | Access |
|---|---|---|
| Object | `Gift__c` | Create, Read, Edit, Delete |
| Object | `Gift_Allocation__c` | Create, Read, Edit, Delete |
| Object | `Fund__c` | Create, Read, Edit, Delete |
| Object | `Appeal__c` | Create, Read, Edit, Delete |
| Field | every custom field on the four objects | Edit, except the read-only fields listed below |
| Field | `Gift__c.Household__c` | Read only (the package derives it, R-G2) |
| Field | rollup targets on `Fund__c` and `Appeal__c` (`Total_Raised__c`, `Total_Raised_This_Year__c`, `Gift_Count__c`, `Last_Gift_Date__c`, `Rollups_Last_Calculated__c`) | Read only |
| Field | rollup targets on Account and Contact (the twelve names in canonical model Section 26) | Read only |
| Tab | Gifts, Funds, Appeals | Visible |
| Apex | `GiftController` | Enabled |
| Apex | `GiftService`, `GiftSelector`, `GiftAllocationSelector`, `FundSelector`, `AppealSelector`, `GivingAccountSelector` | Enabled (they are called from the controller and from the trigger handlers) |
| Apex | `GiftTriggerHandler`, `GiftAllocationTriggerHandler`, `FundTriggerHandler`, `AppealTriggerHandler` | Enabled (the dispatcher instantiates them by name) |
| Custom setting | `Giving_Settings__c` | Written only by `SettingsService`, so no field permissions are needed; the console gates editing on the `Manage_Nonprofit_Settings` custom permission that Core already ships |
| Record type | none | This feature ships no record types |

## Giving_Staff

David enters gifts, records refunds, and sets up the funds and appeals he is about to use.

Same as Giving_Admin, with these differences:

- No Delete on any of the four objects. A fund that has been used is deactivated, not deleted
  (R-F2), and a gift is reversed, not deleted (R-G3).
- Everything else is identical, including create and edit on `Fund__c` and `Appeal__c`, because
  the five-minute walkthrough in `docs/admin-guide/gifts.md` has David creating a fund and an
  appeal before his first gift.

## Giving_Read_Only

Tom and Jen look at the numbers without being able to change them.

| Kind | Entry | Access |
|---|---|---|
| Object | `Gift__c`, `Gift_Allocation__c`, `Fund__c`, `Appeal__c` | Read |
| Field | every custom field on the four objects, and the rollup targets on Account and Contact | Read |
| Tab | Gifts, Funds, Appeals | Visible |
| Apex | `GiftController` | Enabled, so a gift panel loads. `refund` and `writeOff` still fail for these users because the package's DML runs in user mode, which is the intended behavior and is worth a line in the permission set's description. |
| Apex | the selectors listed above | Enabled |

## What the Core permission groups should include once the Module Manager exists

- Turning the Giving module on assigns Giving_Staff to everyone who already holds the Core
  "enter data" group, and Giving_Admin to whoever holds `Manage_Nonprofit_Settings`.
- Turning it off leaves the permission sets in place but removes the tabs from the app, because
  removing a permission set assignment loses an administrator's own edits (Principle 6).
- The Core group that grants `Manage_Nonprofit_Settings` needs no Giving entry: the Giving
  settings are reached through `SettingsService` and the `Setting_Definition__mdt` rows this
  feature ships.

## Notes for the other agents

- **Four fields on `Gift__c` are deliberately absent here.** `Commitment__c` and `Installment__c`
  come from the commitments agent, `Tribute__c` and `Matched_Gift__c` from the soft credits
  agent. They are not on the gift layout: each agent adds its own field to
  `layouts/Gift__c-Gift Layout.layout-meta.xml` when it lands.
- **`Created_By_Import_Batch__c` is a real lookup to Core's `Import_Batch__c`**, per canonical
  model Section 18. The Giving package therefore does not deploy until Core's import framework
  (C-14) has created that object.
- **Two `Giving_Settings__c` keys have no console entry yet.** This feature ships the object and
  all three v0.3 keys, plus `Setting_Definition__mdt` rows for Default Fund, Default Appeal and
  Automatic Household Soft Credits. The commitments agent should ship the two definition rows
  for `Installment_Generation_Horizon_Months__c` and `Installment_Overdue_Grace_Days__c` with
  the feature that reads them.
- **C-03 should add a Lookup data type to `Setting_Definition__mdt` in the v0.2 polish.** Default
  Fund and Default Appeal are record identifiers held as text (ADR-0014), and they ship here as
  `Data_Type__c` Text with a description telling the console to render a picker. A Lookup data
  type would let the console render the picker from the definition instead of from a special
  case, and Maria would never see the difference.
- **Splitting a gift across funds needs the entry screen (G-03).** Allocations always total the
  gift (R-GA1), and the check runs on every save, so a person cannot build a split one row at a
  time in the standard record UI: the first row saved would leave the gift out of balance. The
  entry screen sends the whole split in one save, and `GiftService.suppressDefaultAllocations`
  is the flag it sets so the gift does not also receive a default allocation. The gifts admin
  guide says this in "Common mistakes".
- **The rollup engine writes the target fields listed above**, which are read only for every
  user. The engine must therefore write them in system mode, or be granted its own permission
  set: that is a Core decision (C-13), recorded here because this feature is what creates the
  fields.
