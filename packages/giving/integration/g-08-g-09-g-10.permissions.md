# G-08, G-09, G-10: what the integrator has to wire up

Soft credits (G-08), tributes (G-09), and matching gift linkage (G-10) ship their own objects,
Apex, and components, but four kinds of shared metadata belong to whoever integrates the
iteration, because they are merge conflict magnets and this branch deliberately does not touch
them (plan Section 9.2).

Everything below is a request, not a change.

## 1. Permission set entries

Three permission sets exist in Core: **Nonprofit Admin**, **Nonprofit Staff**, and **Nonprofit
Read Only**. These features need the following added to them.

### Objects

| Object | Nonprofit Admin | Nonprofit Staff | Nonprofit Read Only |
|---|---|---|---|
| `Soft_Credit__c` | create, read, edit, delete | create, read, edit, delete | read |
| `Tribute__c` | create, read, edit, delete | create, read, edit, delete | read |

Staff need create and delete on Soft Credit, not only read: the package's own automation writes
those records in user mode (`AccessLevel.USER_MODE`), so a gift saved by someone without create
access on Soft Credit would fail rather than silently skip the household credit. That is
deliberate, and it is why the entry matters.

### Fields

All fields on both objects, readable and editable for Admin and Staff, readable for Read Only,
with two exceptions that are read only for everyone because the package maintains them:

- `Soft_Credit__c.Is_Automatic__c`
- `Soft_Credit__c.Percent__c` (writable in the API, shown read only on the layout)

New fields on objects Core and Giving already own:

| Field | Nonprofit Admin | Nonprofit Staff | Nonprofit Read Only |
|---|---|---|---|
| `Contact.Employer__c` | read, edit | read, edit | read |
| `Account.Employer__c` | read, edit | read, edit | read |
| `Gift__c.Tribute__c` | read (package maintained mirror) | read | read |
| `Gift__c.Matched_Gift__c` | read, edit | read, edit | read |

### Apex classes

Add to Admin and Staff: `SoftCreditController`, `TributeController`. The services, selectors, and
handlers do not need class access, because nothing outside the package calls them directly.

### Tabs

`Soft_Credit__c` and `Tribute__c` tabs: Visible for Admin and Staff, Available for Read Only.

## 2. Related lists and components on the Gift layout

The Gift page layout is owned by the Giving objects feature (G-01). Two related lists and two
components belong on it:

| Placement | What | Columns or notes |
|---|---|---|
| Related list | Soft Credits | Contact, Account, Role, Amount, Is Automatic |
| Related list | Tributes | Type, Honoree Name, Notification Sent, Notification Sent Date |
| Lightning record page component | `giftSoftCredits` | Right column, above the related lists |
| Lightning record page component | `tributeNotification` | Right column, under the soft credits panel |
| Layout field | `Tribute__c` | Read only; the package maintains it (R-G8) |
| Layout field | `Matched_Gift__c` | Editable; this is how a match is linked (R-G11) |

On the Contact and Account layouts, `Employer__c` belongs in the same section as the
organization's other affiliation information.

## 4. Assumptions this branch made that the integrator should confirm

- **`Rollup_Definition_Default__mdt` field API names.** Six rollup default records ship here
  (`Total_Soft_Credits__c` and `Soft_Credit_Count__c` for the household, account, and contact
  scopes). Their field names are taken from canonical model Section 13 and Section 14, since the
  metadata type itself is built by C-13. If C-13 named a field differently, these six records need
  the same rename.
- **Target filter notation.** The household and account scoped rollups separate their target
  record sets with a filter on `RecordType.DeveloperName`, written in the filter document format
  of R-R2. If the engine expects another way of naming the record type, these records change with
  it.
- **`Giving_Settings__c` and the `Automatic_Household_Soft_Credits__c` key** are created by the
  Giving objects feature. This branch reads the key through
  `SettingsService.getValue('Giving_Settings__c', 'Automatic_Household_Soft_Credits__c')` and
  treats a missing value as on, so it degrades safely if the settings object arrives later.
- **`Gift__c` and its fields** (`Donor_Contact__c`, `Donor_Account__c`, `Amount__c`, `Status__c`,
  `Gift_Date__c`, `Type__c`) come from the same feature. The two lookups this branch adds to that
  object (`Tribute__c`, `Matched_Gift__c`) are separate files, so there is no file level conflict.
- **`GiftTrigger`** is shipped by the Giving objects feature and calls
  `TriggerDispatcher.run('Gift__c')`. This branch adds two registry rows for that object rather
  than touching the trigger: `GiftSoftCreditHandler` at execution order 30 and
  `GiftMatchingGiftHandler` at 40.
