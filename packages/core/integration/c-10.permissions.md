# C-10 permission requirements

This feature does not create or edit permission set files (shared files policy). The
permission set(s) that grant Core access (owned by another feature) need the following
added for the sample data loader to work for an admin.

## Custom permission

- `Manage_Nonprofit_Settings` (already defined elsewhere in Core) gates every action in
  `SampleDataController`. A user without it sees the `sampleDataManager` card in
  read-only mode.

## Apex class access

Only the LWC-facing entry point needs an explicit grant; it calls the rest of the
feature's classes internally, and internal Apex-to-Apex calls do not require their own
permission set entries.

- `SampleDataController`

## Field-level security

Both fields default to hidden until granted. Grant Read and Edit on both so
`SampleDataLoader` (running in user mode) can set them on insert and read them for
counts and removal.

- `Account.Sample_Data__c`
- `Contact.Sample_Data__c`

## Object permissions

The admin's permission set must already carry Create, Read, and Delete on Account and
Contact for the Household model (C-01) to work at all; the sample data loader relies on
that same grant.

One addition for the flexible (junction) membership mode: the loader now joins each sample
person to their household through `HouseholdService.addMembers`, which writes a
`Household_Member__c` row in the running user's own access. The admin's permission set
therefore needs Create and Read on `Household_Member__c`, and Read and Edit on
`Household_Member__c.Household__c`, `.Contact__c`, `.Account__c`, `.Role__c`,
`.Is_Primary__c`, and `.Start_Date__c`. C-01 already grants these for the Members panel, so
in practice this is a dependency to keep rather than a new grant; without it a load in
junction mode fails with a field-level or object-level error rather than loading silently
wrong. Delete on `Household_Member__c` is not needed: removal deletes the sample
households, and the `Household__c` lookup cascades to the rows.

## Cross-branch contracts

C-10 compiles and runs against metadata and Apex owned by other features. Each item below
is what this feature assumes; a mismatch is a deploy-time or run-time failure, so the
owning branch changing any of them has to change C-10 with it.

### Error Log (C-04 / C-08)

`ErrorLogger` is called by `SampleDataController` (once per synchronous failure, at the
LWC boundary) and by both queueables (async failures nothing else sees). C-10 uses only:

- `public static void log(Exception e, String context)`

The class is also expected to offer, and C-10 stays compatible with, the wider contract
other Core features use:

- `public static void log(Exception e, String context, Id recordId)`
- `public static void logMessage(String message, String context, String severity)`

`log` must never throw: it is called from a catch block that then rethrows the original
exception.

### Household membership (C-01)

The loader never writes membership itself. It calls, and stays compatible with:

- `public static Boolean HouseholdService.isJunctionMode()`, to decide whether a sample
  contact carries its own household or is joined by a membership row.
- `public static Set<Id> HouseholdService.addMembers(Map<Id, Set<Id>> personIdsByHouseholdId)`,
  which joins each chunk of sample people to their households in whichever way the mode
  means, and which refuses an account that is not a household.

### Record types (C-01)

Looked up by DeveloperName through `getRecordTypeInfosByDeveloperName`, never by Id, and
a missing one raises `Core_SampleData_RecordTypeMissing` naming the developer name.

| Object | Record type DeveloperName | Used for |
|---|---|---|
| Account | `Household` | The 200 sample households |
| Account | `Organization` | The 25 sample organizations |
| Contact | `Household_Contact` | Every sample person |

### Fields (C-01)

Missing fields are a compile-time failure, not a runtime one: without them the loader
does not deploy at all.

| Field | Type | How C-10 uses it |
|---|---|---|
| `Account.Custom_Name__c` | Checkbox | Set true on the four custom-named households, so the naming trigger does not recompute their names (rule R-H8) |
| `Account.Anniversary__c` | Date | Set from the household's `anniversary` when present |
| `Contact.Household_Role__c` | Picklist | Set to one of `Head`, `Spouse or Partner`, `Child`, `Other`; every value in the generated data must exist in the picklist |
| `Contact.Deceased__c` | Checkbox | Set true on the five deceased sample members |
| `Contact.Preferred_Name__c` | Text | Set when the member has a nickname |
| `Account.Sample_Data__c`, `Contact.Sample_Data__c` | Checkbox | Owned by C-10 (this branch), listed here because the field-level security above applies to them |

C-10 also relies on the household naming automation being present and on for the computed
names and greetings to appear: it inserts every non-custom household with the placeholder
name `Household` and expects the trigger to recompute Name and both greetings once the
members are inserted (rule R-H4). With that automation absent or off, the sample data
loads correctly but 196 households read "Household".

### Settings console (C-03)

`customMetadata/Setting_Definition.Sample_Data.md-meta.xml` will fail to deploy unless
`Setting_Definition__mdt` ships with these fields and values:

| Field | Type | Value used by C-10 |
|---|---|---|
| `Setting_Key__c` | Text | `Sample_Data` |
| `Section__c` | Picklist or Text | `General` |
| `Module__c` | Picklist or Text | `Core` |
| `Data_Type__c` | Picklist | `Component` (the value that means "render a component instead of an input") |
| `Component__c` | Text | `sampleDataManager` |
| `Picklist_Values__c` | Text | left empty |
| `Description__c` | Text | the admin-facing description |
| `Help_Path__c` | Text | `admin-guide/sample-data.md` |
| `Sort_Order__c` | Number | `90` |

### Custom permission (C-06)

- `Manage_Nonprofit_Settings`, as above. `SampleDataController` reads it through
  `FeatureManagement.checkPermission`, so the custom permission has to exist by that API
  name; an org where it does not simply reports that nobody can manage sample data.

## Not required

- No access to `StaticResource` is needed beyond the standard Apex runtime context;
  querying it does not require a separate object permission.
- No access to `Setting_Definition__mdt` records is granted here; the settings console
  that reads them is owned by C-03.
- Person Accounts are not required and are never created. The sample people are contacts
  in both membership modes, because Core cannot depend on Person Accounts (ADR-0013). An
  org can be in junction membership mode with or without Person Accounts enabled; the
  loader asks only about the mode.
