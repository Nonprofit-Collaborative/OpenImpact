# C-03 permission requirements

## Merge order, before anything else

C-03 does not deploy on its own and must not be merged first.

1. **C-04 first.** It ships `Nonprofit_Settings__c`, `Setting_Change__c`, `Error_Log__c`,
   `ErrorLogger`, `AutomationControl` and the `Manage_Nonprofit_Settings` custom permission.
   Every Apex class here compiles against them, the Hub app names the `Error_Log__c` tab, and
   every save is gated on that custom permission.
2. **C-01 next.** It ships the `Households` and `Organizations` list views the two app pages
   are pinned to, and the Setting Definition rows that give the console something to show.
3. **C-03 last.**

Two things to apply at merge:

- C-01's household rows use `Section__c = "Household names and greetings"`. Rename them to
  `Households`, which is the name in `SettingSections` and the one the Setup Assistant's
  "Confirm how households are named" step opens. Every package uses a name from
  `SettingSections.all()`: General, Organization, Households, Giving, Automation, Access,
  Import, Health.
- `scripts/ci/check-apex-offline.sh` is a local tool taken from `main`, not a CI gate. C-03
  adds nothing to `.github/workflows/ci.yml`.

What the Nonprofit Hub and the Nonprofit Settings console need in each packaged permission
set. C-03 ships no permission set files: the integrator merges these entries into
`Nonprofit_Admin`, `Nonprofit_Staff`, and `Nonprofit_Read_Only`.

The custom permission `Manage_Nonprofit_Settings` is created by C-04. C-03 only reads it,
through `FeatureManagement.checkPermission`.

## Nonprofit_Read_Only

Same as `Nonprofit_Staff` with one difference: no object or field is writable anywhere, and
the `Nonprofit_Settings` tab stays visible so that a board member or a bookkeeper can see
how the org is configured without being able to change it.

|---|---|---|

| Custom permission | none | |
| Apex class | the nine classes listed above | |
| Object | `Nonprofit_Settings__c`, `Setting_Change__c` | Read only. |

## Notes for the integrator

- `Setting_Definition__mdt` needs no permission set entry: custom metadata is readable by
  any user with access to the Apex that queries it.
- Following ADR-0017, each package owns its own protected hierarchy custom setting and names
  it on its Setting Definition rows (`Settings_Object__c`, default `Nonprofit_Settings__c`).
  A module's permission set grants access to its own settings object; C-03 grants only Core's.
  `SettingsService` and `SettingsController` are `@NamespaceAccessible` public, not `global`.
- The Households and Organizations tabs are app pages hosting the standard list view
  component pointed at the `Households` and `Organizations` list views that C-01 ships.
  Those list views need to exist for the pages to render.
- Following ADR-0020, a module puts its own settings page in the one console by shipping a
  Setting Definition row with `Data_Type__c = Component`, no `Component__c`, and its Lightning
  tab in `Navigation_Target__c`. That tab has to be visible on the module's own permission set,
  or the console offers a page the user cannot open. Core's own panels are named in
  `Component__c` and are imported by name.
- The audit records are the only user-mode DML: `Setting_Change__c` stays in user mode so an
  org that has locked the audit trail down keeps that control.
