# C-17 Addresses: integration notes

Everything in this file touches a **shared** file that C-17 must not edit directly:
permission sets, the Account and Contact page layouts, and the Nonprofit Hub app. The
owning feature applies these entries. Nothing here changes the behavior of the address
feature itself; it changes who can see it and where it appears.

Section 7.4).

### Read Only

Same list, with **Read** on the object and on every field, no Create, Edit, or Delete, tab
visible, and `AddressController` enabled so the address panel renders. `setDefault` fails
for these users in user mode, which is correct: the panel reports it with
`Core_Address_SetDefaultFailed`.

### Nonprofit Settings

The Addresses section of the settings console is governed by the existing
`Manage_Nonprofit_Settings` custom permission. C-17 adds no new custom permission.

## 2. Page layout placements

### Account page layouts (Household and Organization)

- **Related list:** `Address__c` through the `Addresses` relationship (`Account__c`),
  labelled **Addresses**, columns: Address Number, Type, Street, City, State, Postal Code,
  Default. Sort by Default descending. Place it below the Household Members related list on
  the Household layout and below Contacts on the Organization layout.
- **Component:** the `addressPanel` Lightning web component on the record page, in the main
  column, directly under the highlights panel. The panel is the place a person changes an
  address; the related list is there for reporting and for bulk edits.
- **Second related list:** `Address__c` through the `Personal_Addresses` relationship
  (`Person_Account__c`), labelled **Personal Addresses**, added only on the Person Account
  layout in an org where person accounts are enabled. It is empty and harmless elsewhere.

### Contact page layout (Household Contact)

- **Related list:** `Address__c` through the `Addresses` relationship (`Contact__c`),
  labelled **Personal Addresses**, columns: Address Number, Type, Street, City, State,
  Postal Code, Default.
- **Component:** the `addressPanel` component in the main column under the highlights panel.

### Nonprofit Hub app

Add the **Addresses** tab (`Address__c`) to the Nonprofit Hub app's tab set, after
Organizations. Its list views ship with C-17: All Addresses, Addresses In Use, Seasonal
Addresses, Addresses Not Yet Verified.

## 3. Automation registry

C-17 ships three `Automation_Registry__mdt` records, all with `Execution_Order__c` 20, so
they run after the household naming handlers (order 10) have settled membership:

| Developer name | Object | Handler class |
|---|---|---|
| `Address_Default_Propagation` | `Address__c` | `AddressTriggerHandler` |
| `Contact_Address_Capture` | Contact | `ContactAddressHandler` |
| `Account_Address_Capture` | Account | `AccountAddressHandler` |

C-17 ships the `AddressTrigger` trigger on `Address__c`. It ships **no** Contact or Account
trigger: those exist already and dispatch by registry (ADR-0017).

## 4. Core contracts this feature is written against

These were verified against the Core source after `main` was merged in. They are recorded
here because they are the seams C-17 depends on, not because anything is still open.

| Contract | Shape |
|---|---|
| `TriggerHandler` | Virtual base class. Every context method takes no arguments (`beforeInsert()`, `afterInsert()`, `beforeUpdate()`, `afterUpdate()`, `beforeDelete()`, `afterDelete()`, `afterUndelete()`); a handler extends it, marks its methods `override`, and reads the records through `newRecords()`, `newRecordsById()`, `oldRecords()`, `oldRecordsById()`. The three C-17 handlers do exactly this. |
| `TriggerDispatcher.run(String)` | Called from `AddressTrigger` with the literal `Address__c`. |
| `ErrorLogger.log(Exception, String)` | Exception first, context string second. |
| `SettingsService.getSettings()` | Returns `Nonprofit_Settings__c`. |
| `HouseholdService.getMemberPersonIds(Set<Id>)` | Returns `Map<Id, Set<Id>>` keyed by household id, values the member person ids. |
| `HouseholdService.getHouseholdIdsFor(Set<Id>)` | Returns `Map<Id, Id>`: one household per person, null where the person has none. `AddressService` reads it that way. |
| `OrgShapeDetector.detect()` | Returns an org shape with `hasPersonAccounts` (Boolean) and `personAccountRecordTypeIds` (`Set<Id>`), computed once per transaction. |
| Test data | `HouseholdTestDataFactory.newHousehold(String)`. C-17 ships `AddressTestDataFactory` for its own household, organization, and contact helpers rather than editing the shared `TestDataFactory`. |
| `Automation_Registry__mdt` | Fields `Handler_Class__c`, `Object_Name__c`, `Execution_Order__c`, `Enabled_By_Default__c`, `Description__c`. |
| `Setting_Definition__mdt` | Fields `Settings_Object__c`, `Setting_Key__c`, `Section__c`, `Data_Type__c`, `Picklist_Values__c`, `Description__c`, `Module__c`, `Sort_Order__c`, `Help_Path__c`. There is no default value field: the shipped default lives on the custom setting field itself. |
| `SettingSections.ADDRESSES` | The `Addresses` section already exists in Core, so C-17 adds no section. |

### One thing for the integrator to settle, outside C-17

Every `Automation_Registry__mdt` record already on `main` writes `<field>Default_Enabled__c</field>`,
but the field on the object is `Enabled_By_Default__c` (`Naming_Pattern__mdt` is the object that
has `Default_Enabled__c`). C-17's three records use `Enabled_By_Default__c`, which is the field
that exists. The pre-existing records need the same correction or the registry will not deploy;
that fix belongs to whoever owns the trigger framework metadata, not to this branch.

## 5. Settings key typing

The canonical model types `Contact_Address_Change_Behavior__c` as a picklist, and a custom
setting field cannot be a picklist. C-17 ships it as Text(40), with the two choices offered by
the settings console through its `Setting_Definition__mdt` record and with the code treating
anything blank as "Update household". This is the pattern ADR-0019 already settled for every
picklist-typed setting key, so C-17 needs no ADR of its own.
