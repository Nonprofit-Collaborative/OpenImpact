# Integration notes: C-09 (household merge and split)

For the integrator. This branch stacks on the households branch (C-01, C-02, C-08) and
touches no permission set file and no Nonprofit Hub app. Everything those files need from
merge and split is listed here.

Everything the household branch already asks for (see `c-01-c-02-c-08.permissions.md`)
still applies. Merge and split add these.

## 2. Custom permission

**None.** This feature deliberately does not check `Manage_Nonprofit_Settings` or any other
custom permission.

The decision, recorded here because it is the sort of thing a reviewer will ask about:
**anyone who can edit both households may merge or split them.** The check is
`UserRecordAccess.HasEditAccess` on each record, so it is a record level check that honors
sharing rather than an object level one. Reasons:

1. Merging duplicates is data cleanup, and plan Section 2.2 has both Maria (Operations
   Manager) and David (Development Director) doing data cleanup. Gating it on the
   administrator permission would send David to Maria for every duplicate an import made.
2. A person who can already edit two household records can already achieve the same outcome
   by hand, one contact at a time. A permission that only slows the safe path down does not
   protect anything.
3. The irreversibility is handled where it belongs: a confirmation screen that names both
   households and says a merge cannot be undone.

An org that wants merging restricted restricts edit access on households, which is a
standard sharing decision, not a new permission to learn.

## 4. Quick action and layout placement

`quickActions/Account.Merge_Household.quickAction-meta.xml` ships a
`LightningWebComponent` action of the `householdMergeSplit` component, labelled "Merge or
split". A packaged quick action is not on any layout by itself.

Two ways to surface it, either of which the integrator may choose:

1. **Lightning record page (preferred).** Drop the **Household Merge and Split** component
   onto the Household record page in the Lightning App Builder. The component is exposed for
   `lightning__RecordPage` on Account, and it shows the "this is an organization" notice on
   an Organization record, so it is safe on a shared page.
2. **Page layout.** Add `Merge_Household` to the Salesforce Mobile and Lightning Experience
   Actions section of `layouts/Account-Household Layout.layout-meta.xml`. That file belongs
   to the households branch, so this branch does not edit it. The component is also exposed
   for `lightning__RecordAction` (ScreenAction), which is what makes the quick action work.

The admin guide tells Maria to ask for one of these if the button is not there, and names
both.

## 5. Classes this branch calls but does not ship

The same stubs the households branch needed, unchanged and still uncommitted:
`TriggerDispatcher`, `TriggerHandler`, `AutomationControl`, `ErrorLogger`,
`SettingsService`, `OrgShapeDetector`, `TestDataFactory`, plus the `Nonprofit_Settings__c`
custom setting with its eight fields. The contracts relied on here are the ones already
listed in `c-01-c-02-c-08.permissions.md`, plus:

- `ErrorLogger.log(Exception e, String context, Id recordId)` for a merge or split that
  fails. A merge that succeeds is not logged: the platform records an account merge in the
  survivor's own history, which is the audit trail a person can read, and a second log of
  our own would be a duplicate that can drift.

## 6. What other packages may call

`HouseholdMergeService` is `public` and `@NamespaceAccessible` with its public members
annotated, on the same footing as `HouseholdService`.

This branch also adds four methods to `HouseholdService`, all `@NamespaceAccessible`:

- `afterMembershipChange(Set<Id> householdIds)`: the one hook every caller that moves
  membership calls afterwards. Today it recounts members and reapplies naming. **The rollup
  adapter in v0.2 extends this method rather than adding a second hook**, so that no caller
  has to learn that rollups exist.
- `moveMembers(Set<Id> personIds, Id targetHouseholdId)`: bulk move in either membership
  mode, answering with every household touched. Does not recount or rename; the caller
  settles up once with `afterMembershipChange`. `moveContact` now delegates to it, so its
  behavior is unchanged.
- `createHouseholdFor(List<HouseholdService.Person> members)`: creates one household named
  from the people about to join it, for a split with no destination.

## 7. Settings fields this branch reads

`Delete_Empty_Households__c` only, and only through
`HouseholdService.deleteEmptyHouseholds`. Everything else it needs comes from the household
branch's own reads.

## 8. What could not be verified without an org

No org exists in the build environment. These two behaviors are argued from the platform
documentation and are compile checked, not run:

1. `Database.merge(master, victimId, allOrNone, AccessLevel.USER_MODE)` between two Accounts
   that carry the same `Household` record type. Merging accounts of different record types
   is what Salesforce restricts, and this branch refuses two records unless both carry the
   Household record type, so the restriction should never be reached. Worth confirming in
   the first scratch org.
2. What the platform merge does to `Household_Member__c` rows that still point at the
   household being merged away. This branch does not rely on the answer: every membership
   is repointed or end dated before the merge runs, so no current membership row should be
   left aimed at the record that goes away. Confirm that ended rows survive the merge as
   history rather than being reparented, which is the behavior the guide implies.
