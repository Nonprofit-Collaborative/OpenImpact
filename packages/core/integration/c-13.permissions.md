# C-13 permission requirements

This feature does not create or edit permission set files (shared files policy). The
permission sets that grant Core access (owned by another feature) need the following added
for the rollup engine and its console page to work.

## Custom permission

- `Manage_Nonprofit_Settings` (already defined elsewhere in Core) gates every write in
  `RollupController`. A user without it still opens the Rollups page and still sees every
  total and its last calculated time; the controls are read only. No new custom permission
  is introduced.

## Apex class access

Only the LWC-facing entry point needs an explicit grant; it calls the rest of the feature's
classes internally, and internal Apex-to-Apex calls do not require their own entries.

- `RollupController`

## Object permissions

`Rollup_Definition__c` is configuration an administrator manages as a list.

- **Nonprofit Admin:** Read, Create, Edit, Delete on `Rollup_Definition__c`.
- **Nonprofit Staff and Nonprofit Read Only:** Read on `Rollup_Definition__c`, so the
  Rollups page opens read only rather than erroring, which is what the read-only notice on
  the page promises.

No grant is needed on `Rollup_Definition_Default__mdt`: it is package-shipped custom
metadata, read by `RollupSelector` in system mode, and it is never shown to a user.

## Field-level security

Every field on `Rollup_Definition__c` defaults to hidden until granted. Grant Read on all
of them to all three permission sets, and Edit to Nonprofit Admin only:

`Name`, `Description__c`, `Definition_Key__c`, `Source_Object__c`, `Target_Object__c`,
`Relationship_Path__c`, `Aggregate__c`, `Source_Field__c`, `Order_By_Field__c`,
`Target_Field__c`, `Filter_JSON__c`, `Target_Filter_JSON__c`, `Fiscal_Year_Aware__c`,
`Fiscal_Year_Offset__c`, `Fiscal_Date_Field__c`, `Mode__c`, `Last_Calculated__c`,
`Is_Package_Default__c`, `Active__c`.

`Last_Calculated__c` and `Is_Package_Default__c` are written by the package in system mode
(`RollupWriter`), so Read is enough for every permission set including the admin's; they
are listed above with the rest because the page shows them.

## Nothing is granted on the vendored engine

The vendored apex-rollup types and objects (`Rollup__mdt`, `RollupControl__mdt`,
`RollupSettings__c`, `RollupState__c`, and the rest) take no permission set entries and
must not be given any. The administrator never sees them, which is the promise ADR-0015
makes: the adapter builds `Rollup__mdt` in memory for the length of one call and no record
of it is ever created in a subscriber org. Granting access to them would put a second
rollup configuration surface in front of the administrator, which is exactly what the
decision rejected.

Vendored Apex is likewise not granted: nothing outside Core's own `Rollup*` classes calls
it, and no vendored invocable action or LWC ships.

## Automation

Two `Automation_Registry__mdt` rows register `RollupTriggerHandler` against Contact and
`Household_Member__c` at execution order 90, after the household upkeep that runs at lower
orders. They need no permission grant: the dispatcher runs them, and an administrator
switches them off from the Automation page, which is where every packaged automation is
switched off.

## Scheduled job

`RollupScheduler` schedules the `Open Impact Rollups` job from the Rollups page. Starting
and stopping it needs no permission beyond `Manage_Nonprofit_Settings`, which is already
checked in `RollupController.setSchedule`. No Setup access is required of the
administrator, which is the point.

## Applied at merge

Nothing yet. The permission set owner applies the object and field entries above in the
same release that ships this feature.
