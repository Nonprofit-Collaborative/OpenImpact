**Lightning record pages**

This branch ships three FlexiPages: `Household_Record_Page` and `Organization_Record_Page`
(Account) and `Household_Contact_Record_Page` (Contact). A FlexiPage cannot say which record
type it serves: the assignment lives in the Lightning app, which C-03 owns. The Nonprofit Hub
app needs these `actionOverrides` entries, one per record type and form factor (Large for the
desktop, Small for the phone):

```xml
<actionOverrides>
    <actionName>View</actionName>
    <comment>Household</comment>
    <content>Household_Record_Page</content>
    <formFactor>Large</formFactor>
    <pageOrSobjectType>Account</pageOrSobjectType>
    <recordType>Account.Household</recordType>
    <type>Flexipage</type>
</actionOverrides>
```

with the same block repeated for: Account.Household at `formFactor` Small; Account.Organization
at Large and Small pointing at `Organization_Record_Page`; and Contact.Household_Contact at
Large and Small pointing at `Household_Contact_Record_Page`. Without those six entries the
household walkthrough fails at step 4, because the members panel is nowhere on the page.

`Household_Record_Page` references the `householdMembersPanel` component, which the stacked
LWC branch adds. The two branches deploy together.

## 6. What other packages may call

Per ADR-0017 these three classes are `public` and `@NamespaceAccessible`, with their public
members annotated: `HouseholdService`, `HouseholdNamingService`, `HouseholdSelector`. The
contract the Giving package asked for is:

- `HouseholdService.getHouseholdIdsFor(Set<Id> personIds)` returning `Map<Id, Id>`. The set
  may mix people stored as contacts and people stored as accounts. Every id asked about is
  in the answer, with null where the person has no household. Answers are cached for the
  transaction and the cache is cleared whenever this service changes membership.
- `HouseholdService.getMemberPersonIds(Set<Id> householdIds)` returning `Map<Id, Set<Id>>`.
- `HouseholdService.Person`, the shape a member is presented in, whichever object holds them.
- `HouseholdService.afterMembershipChange(Set<Id> householdIds)`, the one entry point for
  household upkeep: it recounts the members, rewrites the name and the two greetings, and
  tidies away a household left with nobody in it. The trigger handlers call it, and a package
  that changes membership itself calls it afterwards. An overload takes a second argument
  saying whether an emptied household may be tidied away.

## 7. What is owned elsewhere

- **Sample data.** This feature adds `Household_Member__c` and three record types, and the
  sample data set is not updated here: that belongs with the sample data feature (C-10). The
  definition of done item is open until it does.
- **Choosing the membership mode automatically.** `households.md` says the product notices an
  org that stores people as accounts and picks the flexible mode. This branch reads the answer
  from `OrgShapeDetector` and the setting; deciding and writing the setting on install belongs
  to the Setup Assistant and the detection feature.
- **The shipped naming patterns.** `Naming_Pattern__mdt` records ship here, and the post
  install script that materializes the default ones into `Nonprofit_Settings__c` belongs with
  the settings feature. Until it runs, `HouseholdNamingService` falls back to the same three
  patterns in code, and the two copies must be kept in step.

## 8. The one documented exception to the user mode rule

ADR-0021 is the authority, and `HouseholdWriter` is one of the writer classes it names. It
writes the household name, the two greetings and the member count in system mode: those
fields are computed by the package, nobody types them, and writing them with the saving
user's own access turns an ordinary contact save into a raw DML error for any user a packaged
permission set cannot reach. The full reasoning is in the class header.

`HouseholdSelector` has two kinds of read and keeps them apart. The upkeep reads, which feed
the count and the naming, run in system mode for the same reason as the write they feed. The
`ForDisplay` reads, which are what `HouseholdController.getMembers` returns to the members
panel, check object access and strip every field the running user cannot read, so a member's
deceased flag or preferred name never reaches somebody who could not read it on the record.
`HouseholdServiceTest.aScreenNeverShowsAFieldTheUserCannotRead` proves it.

Every class involved is `with sharing`, so which records a user can reach is unchanged, and
everything a person types (a contact, a membership row, a move) is still saved in user mode.

**One amendment to ADR-0021 travels with this branch.** The branch predates the ADR landing on
`main`, so it carries the file with exactly two additions, both in the Decision section: that a
read feeding one of these writes may run in system mode while reads that reach a user stay in
user mode, and that a writer may narrow `without sharing` to `with sharing` where its work must
never cross sharing. Resolve the merge by keeping `main`'s file plus those two additions;
nothing else in the file differs.

## 9. Settings fields this branch reads

All on `Nonprofit_Settings__c`, all already in the canonical model Section 12:
Household_Membership_Mode__c, Auto_Create_Households__c, Delete_Empty_Households__c,
Household_Name_Pattern__c, Formal_Greeting_Pattern__c, Informal_Greeting_Pattern__c,
Include_Deceased_In_Name__c.

Create_Households_For_Person_Accounts__c was one of these and is retired by ADR-0037:
automatic household creation is governed by Auto_Create_Households__c in both membership
modes, and the field, its console row and every read of it are gone.
