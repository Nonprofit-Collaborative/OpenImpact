# C-06 Access page: what the packaged permission sets must contain

The three packaged permission sets, `Nonprofit_Admin`, `Nonprofit_Staff`, and
`Nonprofit_Read_Only`, ship on the C-04 branch (pull request #8) and are resolved at
integration. This branch does not edit them, so this file is the contract: it lists
exactly what must be added to them for the Access page to work, and it is applied when the
two branches meet.

## Nonprofit_Admin

### User permissions

| Permission (API name) | Why C-06 needs it |
|---|---|
| `AssignPermissionSets` | Insert and delete `PermissionSetAssignment`. This is the permission that lets a person who is not a System Administrator give a role and take it away. Without it the user-mode DML in `AccessService.assignRole` and `AccessService.removeRole` fails. |
| `ViewSetup` | Query `PermissionSetGroup` and `PermissionSetAssignment` at all. Both are Setup entities: a user without View Setup and Configuration cannot read them, so the role cards would be empty and every change would fail at the lookup. |
| `ViewAllUsers` | See colleagues in the search box and in the role lists. User records are governed by their own sharing, and in an org where the User object is private a person would otherwise only find themselves. |

Nothing broader is required, and nothing broader should be granted. In particular
`ManageUsers` and `ModifyAllData` are not needed: the Access page never creates,
deactivates, or edits a user, and the admin guide sends Maria to Setup for that.

```xml
<userPermissions>
    <enabled>true</enabled>
    <name>AssignPermissionSets</name>
</userPermissions>
<userPermissions>
    <enabled>true</enabled>
    <name>ViewAllUsers</name>
</userPermissions>
<userPermissions>
    <enabled>true</enabled>
    <name>ViewSetup</name>
</userPermissions>
```

### Custom permission

| Custom permission | Why |
|---|---|
| `Manage_Nonprofit_Settings` | `AccessController` calls `FeatureManagement.checkPermission('Manage_Nonprofit_Settings')` before any change and returns a structured refusal without it. It is also what puts the page into read-only mode rather than edit mode. |

```xml
<customPermissions>
    <enabled>true</enabled>
    <name>Manage_Nonprofit_Settings</name>
</customPermissions>
```

### Apex class access

Every class C-06 ships that a user reaches, directly or through the component. Test
classes are deliberately absent: they need no assignment.

```xml
<classAccesses>
    <apexClass>AccessController</apexClass>
    <enabled>true</enabled>
</classAccesses>
<classAccesses>
    <apexClass>AccessService</apexClass>
    <enabled>true</enabled>
</classAccesses>
<classAccesses>
    <apexClass>PermissionSetAssignmentSelector</apexClass>
    <enabled>true</enabled>
</classAccesses>
<classAccesses>
    <apexClass>PermissionSetGroupSelector</apexClass>
    <enabled>true</enabled>
</classAccesses>
<classAccesses>
    <apexClass>UserSelector</apexClass>
    <enabled>true</enabled>
</classAccesses>
```

## Nonprofit_Staff and Nonprofit_Read_Only

These two sets must carry `ViewSetup` and the Apex class access listed above, and nothing
else from this file. They must not carry `AssignPermissionSets`, and they must not carry
`Manage_Nonprofit_Settings`.

Why `ViewSetup`: `PermissionSetGroup` and `PermissionSetAssignment` are Setup entities, so
without it a staff or read-only user cannot read them at all, and the Access page renders
five empty cards. The admin guide promises that the page "shows you, at a glance, who
currently holds each role", and read-only means read, not blank. `ViewSetup` grants no
ability to change anything: it is the platform's "View Setup and Configuration".

```xml
<userPermissions>
    <enabled>true</enabled>
    <name>ViewSetup</name>
</userPermissions>
```

Plus the same five `classAccesses` entries as above, so the page can call its controller.
`ViewAllUsers` is deliberately not granted to these two: a staff user has no search box to
fill, so they only need to read the role lists, and those come back through the assignment
query rather than through a User search.

If a decision is later taken not to grant `ViewSetup` to staff, nothing breaks: the page
already handles that case and shows `Core_Access_ErrorRolesNotVisible` ("You can see this
page but you cannot see who holds each role...") instead of empty cards. But then the "at a
glance" sentence in `docs/admin-guide/access.md` must be corrected in the same change.

## Other cross-feature contracts this branch depends on

Not permission set entries, listed here so that the whole set of assumptions C-06 makes is
written down in one place.

| Contract | Owner | Used at | Exact shape assumed |
|---|---|---|---|
| `ErrorLogger.log(Exception e, String context)`, public static, void | C-05 | `AccessService.logAndWrap`, `CorePostInstall.assignAdminRoleToInstaller` | Two arguments in that order; never throws |
| `Setting_Definition__mdt` | C-03 | `customMetadata/Setting_Definition.Access_Manager.md-meta.xml` | Fields `Setting_Key__c`, `Section__c`, `Module__c`, `Data_Type__c` (with the value `Component`), `Picklist_Values__c`, `Component__c`, `Description__c`, `Help_Path__c`, `Sort_Order__c`; the console renders the named component for a `Component` row |
| The Nonprofit Settings console | C-03 | Renders `accessManager` from the record above | The component is given no public properties, so it needs no API contract |
| The three permission sets | C-04, pull request #8 | The five permission set groups in this branch reference them by name | `Nonprofit_Admin`, `Nonprofit_Staff`, `Nonprofit_Read_Only` |

## What C-06 does not need

- No object or field permissions. The Access page touches only `User`,
  `PermissionSetGroup`, and `PermissionSetAssignment`, all of which are governed by the
  three user permissions above rather than by object permissions in a permission set.
- No tab visibility. The page is rendered inside the Nonprofit Settings console by the
  `Access_Manager` record of `Setting_Definition` (feature C-03), not by a tab of its own.

## Note for whoever merges this

`AccessControllerTest` gives its test user the `Nonprofit_Admin_Group` permission set
group and then runs as them. Those tests are the check that this file has been applied:
if `Nonprofit_Admin` is missing any of the three user permissions or the custom
permission, they fail.

`CorePostInstall` is what gives the first admin the Nonprofit Admin role at install and at
every upgrade, so the org is never in a state where nobody can open the page.
