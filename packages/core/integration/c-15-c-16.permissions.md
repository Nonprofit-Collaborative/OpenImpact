# C-15 Relationships and C-16 Affiliations: integration notes

Everything in this file touches a **shared** file that these two features must not edit
directly: permission sets, the Account and Contact page layouts and record pages, and the
Nonprofit Hub app. The owning feature applies these entries. Nothing here changes the
behavior of either feature; it changes who can see them and where they appear.

**Edit on the two package maintained fields is required, not optional.**
`Reciprocal_Relationship__c`, `Reciprocal_Type__c`, and `Primary_Affiliation__c` are written
by the package on the saving user's behalf, in user mode. A user who can create a
relationship but cannot edit `Reciprocal_Relationship__c` gets a save that fails after the
other side has been created, which is the worst of both. Read only users need read on all
three and edit on none, because they cannot save anything that would write them.

### Read Only

The same list with **Read** on both objects and every field, no Create, Edit, or Delete, both
tabs visible, and `RelationshipController` and `AffiliationController` enabled so the two
cards render. `removeRelationship` and `makePrimary` fail for these users in user mode, which
is correct: the cards report it with `Core_Relationship_RemoveFailed` and
`Core_Affiliation_MakePrimaryFailed`.

## 2. Page layout and record page placements

### Contact page layout (Household Contact)

- **Component:** `relationshipPanel` in the main column, under the highlights panel.
- **Component:** `affiliationPanel` directly below it.
- **Related list:** `Relationship__c` through the `Relationships` relationship
  (`Contact__c`), labelled **Relationships**, columns: Relationship Number, Related Person,
  Type, Status, Start Date, End Date.
- **Related list:** `Affiliation__c` through the `Affiliations` relationship (`Contact__c`),
  labelled **Affiliations**, columns: Affiliation Number, Organization, Role, Status,
  Primary, Start Date, End Date.
- **Field:** `Primary_Affiliation__c` on the layout, read only to everyone. The package
  maintains it; typing in it is overwritten on the next affiliation save.

### Account page layouts

- **Organization layout:** the `affiliationPanel` component under the highlights panel, and a
  related list of `Affiliation__c` through the `Affiliations` relationship (`Organization__c`)
  labelled **Affiliations**, columns: Affiliation Number, Person, Role, Status, Start Date,
  End Date.
- **Person Account layout** (only in an org where person accounts are enabled): the
  `relationshipPanel` and `affiliationPanel` components, plus related lists through the
  `Person_Relationships` (`Person_Account__c`), `Related_Person_Relationships`
  (`Related_Person_Account__c`), and `Personal_Affiliations` (`Person_Account__c`)
  relationships. They are empty and harmless in an org without person accounts.
- **Household layout:** neither component. A relationship is between people and an affiliation
  is a person's, so neither belongs on the household.

### Nonprofit Hub app

Add the **Relationships** and **Affiliations** tabs to the Nonprofit Hub app's tab set, after
Addresses.

## 3. Automation registry

| Developer name | Object | Handler class | Order |
|---|---|---|---|
| `Relationship_Validation` | `Relationship__c` | `RelationshipValidationHandler` | 10 |
| `Relationship_Reciprocal` | `Relationship__c` | `RelationshipMaintenanceHandler` | 30 |
| `Affiliation_Validation` | `Affiliation__c` | `AffiliationValidationHandler` | 10 |
| `Affiliation_Primary` | `Affiliation__c` | `AffiliationMaintenanceHandler` | 30 |

Two bands, and the reason for each. Order 10 is the band already used for the automations that
put a record's own fields right before it is saved (household naming, membership), so the
validation rows sit there and, being the lowest number on either object, run first. Order 30 is
above the bands already in use (10, and 20 for address capture and propagation) and below 40,
leaving a later feature room to register a handler on either object before or after the
maintenance one without renumbering anything. The gap between 10 and 30 is deliberate: a later
feature that has to see a settled, validated record but must run before the other side is
written has 20 to register at.

The two developer names that already shipped, `Relationship_Reciprocal` and
`Affiliation_Primary`, keep their names. The name is what an `Automation_Setting__c` row and
every `AutomationControl.bypass` call are keyed on, so keeping them means an existing org's
choice about the maintenance automation survives the upgrade, and `ensureDefaults` materializes
only the two new validation rows.

Both features ship their own trigger and neither ships a Contact or Account trigger: those
exist already and dispatch by registry (ADR-0017). One trigger per object is unchanged: a
second registry row is not a second trigger, and `TriggerDispatcher.run` runs every registered
handler for the object in execution order.

### Two switches per object, so validation outlives the upkeep

Each object ships two registry rows: the checks and the upkeep. Switching the upkeep off from
the Automation page leaves every rule running. That matters at the one moment an administrator
is most likely to reach for the switch: before a bulk import, when the duplicate check, the
self reference check, the overlap check, and the status and date rules are exactly what is
needed. An earlier revision of this document argued for one row per object on the grounds that
fewer switches are easier to read; the product owner reversed it, because a switch that quietly
disables validation is worse than an extra line on a page.

The reciprocal setting (`Relationship_Auto_Reciprocal__c`) is unchanged and still turns the
mirroring off without touching the checks. It remains the control the admin guide points an
administrator at first; the automation switch stays the emergency stop.

### Where the split falls, and what the services stand down

The seam is the before/after line, with one deliberate exception to the obvious reading:
`applyDefaults` goes with the validation handler, not with the maintenance one. It looks like
maintenance, but the status and date rule (R-RL5, R-AF4) is one of the rules that has to
survive the upkeep being switched off, and both defaults write only the record in front of the
person saving it. Validation does not read anything `applyDefaults` writes, so the two could
have been separated; they are kept together because the rule they carry belongs with the rules.

Both services now stand **both** of their object's automations down while they write. Before
the split, `AutomationControl.bypass('Relationship_Reciprocal')` stood down the single handler
and so suppressed validation on the package's own writes; after the split that name reaches
only the maintenance handler, so `RelationshipService.withoutReentry` and
`AffiliationService.clearFlags` bypass the validation name as well and clear both in the same
`finally`. Without that, the mirror this package builds would be validated on the way in and a
mirrored record could be refused as a duplicate of the very record it mirrors, which is a
behaviour change the split was not meant to make. The recursion story is otherwise unchanged:
the package's own write never reaches the trigger that made it.

### Class access

The four handler classes are instantiated by `TriggerDispatcher` through `Type.forName`, never
called from a page or a controller, so none of them needs an entry in any permission set. No
`permissionsets/*` file changes for this split.

## 4. Core contracts these features are written against

Verified against Core on `main` at the time of writing.

| Contract | Shape |
|---|---|
| `TriggerHandler` | Virtual base class. Every context method takes no arguments; a handler extends it, marks its methods `override`, and reads records through `newRecords()`, `newRecordsById()`, `oldRecords()`, `oldRecordsById()`. All four handlers do exactly this. |
| `TriggerDispatcher.run(String)` | Called from each trigger with the literal object name. |
| `AutomationControl.bypass` / `clearBypass` | Keyed on the registry `DeveloperName`, which is what the dispatcher checks. Both services bypass their object's two registry names, the maintenance one and the validation one, and clear both in a `finally` block. |
| `ErrorLogger.log(Exception, String)` | Exception first, context string second. |
| `SettingsService.getSettings()` | Returns `Nonprofit_Settings__c`; never null, and empty on a fresh org, which is why the reciprocal setting is read as "anything that is not an explicit false". |
| `SettingSections.RELATIONSHIPS` | Already exists in Core, so C-15 adds no section. |
| `Automation_Registry__mdt` | Fields `Handler_Class__c`, `Object_Name__c`, `Execution_Order__c`, `Enabled_By_Default__c`, `Description__c`. |
| `Setting_Definition__mdt` | Fields `Settings_Object__c`, `Setting_Key__c`, `Section__c`, `Data_Type__c`, `Description__c`, `Module__c`, `Sort_Order__c`, `Help_Path__c`. |

## 5. What could not be verified here

- **No Apex test has been executed.** No Salesforce org exists in this environment, so the 49
  Apex tests these two features ship compile clean against apex-ls and have never run. Run
  them before the iteration is tagged.
- **No person account org.** The person account paths are exercised with ordinary accounts in
  the `Person_Account__c` lookups, which runs the same code (nothing in either feature reads a
  person account field), but a real person account org has not been tried.
- **The overlap rule reads role as free text.** `Role__c` is text, so "Board chair" and "Board
  Chair" are the same role to the overlap check (it trims and lowercases) but "Chair of the
  board" is a different one. That is the right trade for a field an org writes in its own
  words, and it means the rule catches the common mistake rather than every mistake.

## 6. Sample data

Neither feature adds records to the sample data set, deliberately. The five-minute walkthrough
on each admin-guide page is "enter one and watch what happens", and a sample data set that
already carried relationships and affiliations would hide the exact behavior the walkthrough
exists to show. The walkthroughs use the sample households and organizations that are already
loaded (the Garcia family, The Union Foundation, Summit Congregation).
