# v0.1: a nonprofit data model that runs on a Platform-only org

**Date:** 2026-09-08
**Packages changed:**

- Open Impact Core, no package version created (namespace deferred, plan Section 4.3)
- Open Impact Giving, no package version created (v0.2 and v0.3 work, listed here because
  it is on `main`)

This is the internal iteration report. The admin-facing lines are collected in
`v0.1-draft.md` and the six `v0.1-draft-*.md` files, and are assembled into the public
release notes when a version is promoted.

Read the two honesty sections first: **Org shapes passing** and **Open risks**. A Dev Hub
and a long lived test org now exist, and continuous integration deploys into that org on
every push to `main`. **No deployment has yet succeeded**, so nothing below has run in a
Salesforce org: everything is verified by static checks, Jest and an offline compiler.

## Tests and coverage

| Package | Apex tests | Apex coverage | Jest tests |
|---|---|---|---|
| Core, Open Impact code | 601 test methods across 70 test classes | Not measured | 200 across 24 suites |
| Core, vendored apex-rollup | 531 test methods across 19 test classes | Not measured | None |
| Giving | 181 test methods across 22 test classes | Not measured | 43 across 5 suites |

**Apex coverage is not measured, and no Apex test has ever been executed.** The reason has
changed since this report was first written, and the new reason is worse. There is now a Dev
Hub, a long lived test org, and an `org-tests` job that authenticates it, deploys in stages
and runs the Apex tests. It has never got as far as running one: **`packages/core` fails to
deploy with an `UNKNOWN_EXCEPTION`, zero components deployed and zero component errors**, so
the failure names nothing to fix. Another session is working on that as this report is
written. The 782 Apex test methods in Open Impact's own code are still verified only by an
offline compiler that checks syntax, types and unknown classes. The 90 percent target in plan
Section 7.2 is unmet and unmeasured, and that is still the single largest gap.

Jest tests do run, on every push. 243 pass across 29 suites, and none is skipped.

The Apex counts here cover everything on `main`, which includes the v0.2 and v0.3 features.
They are not a count of v0.1 alone.

**No shape has passed, because no deploy has succeeded.** The `org-tests` job runs on a push
to `main` or on a manual run, never on a pull request, because a pull request's code deployed
into the one test org would leave it holding unmerged work. It carries a single global
concurrency group and does not cancel in progress runs, because a half deployed package
persists in an org that is never thrown away.

One documentation contradiction found while writing this and left for the owner:
`docs/contributor-guide/scratch-orgs.md` says the `nonprofit-cloud` shape runs when it is
named in an `SF_ORG_TEST_SHAPES` repository variable. No such variable is read by
`.github/workflows/ci.yml`, which no longer has a shape matrix at all.

## Open risks

**Nothing has been deployed, and the first attempt failed with nothing attached to it.**
This was previously "no Dev Hub exists". That part is **resolved**: a Dev Hub is connected, a
long lived test org secret is set, and continuous integration authenticates that org, deploys
the vendored engine, then Core, then Giving in separate stages, and runs the Apex tests. What
replaced it is narrower and more concrete: the Core stage fails with an `UNKNOWN_EXCEPTION`
before any component is evaluated, which is a Salesforce side failure rather than a named
component error. Staged deployment was added precisely so a failure names a stage rather than
sitting behind all 982 components at once. Until that stage passes, every statement in this
repository about runtime behavior is reasoning, not observation: unknown fields inside SOQL,
validation rules that fight each other, layout and permission set references that do not
resolve, and governor limits under real data volume are all still unchecked. Owned by the
builder, in progress in a separate session.

**The test org is long lived, and that costs something.** A scratch org per run is a clean
room; this org accumulates. Deleted metadata is not removed by a deploy, so a class or a field
deleted here still exists there, and a test can pass because of something an earlier run left
behind. It is a scratch org, so Salesforce deletes it at 30 days and every run after that
fails at login until the secret is replaced. When a result looks surprising, recreating the
org is the first thing to try, not the last. Owned by Brandon, who holds the secrets.

**Two defects reached `main` that only a reviewer caught, not a gate.** Three Automation
Registry records named a field belonging to a different custom metadata type, which would
have refused the entire package deployment; and the household merge destroyed the records it
claimed to merge, invisibly, because the call was not all or nothing and its result was never
read. The first is now gated by `scripts/ci/check-custom-metadata.py`, which checks 118
records. The second is the kind of defect no static check will ever catch, which is the
argument for a working deploy rather than for another script. Owned by the builder.

**Untested code paths that destroy data.** Household merge, household split, and the sample
data remove action all delete or reparent records, and none has been executed. Do not run any
of them against real data before the Apex tests have run in an org. Owned by Brandon, as the
person who will be tempted.

**A correctness defect shipped to `main` and was found by the next feature, not by review.**
The packaged giving rollups filtered gifts on `Status equals Received` while the package
itself writes `Refunded` onto a fully refunded gift's original, so a refunded donor's totals
went negative rather than to zero. It is fixed, in the rollups and in the packaged reports,
and recorded in ADR-0022 and ADR-0023. It is listed here because it is the first defect in
this project that made a number wrong rather than making something fail to work, and no
static check could have caught it. `v0.2.md` and `v0.3.md` carry the detail. Owned by the
builder.

**The name.** "Open Impact" is in use, including by a foundation doing open source work,
which is close enough to this project to be a real conflict. The name is in the repository
name, the package names, the app name, the label prefixes and the documentation. Renaming
gets more expensive every iteration. Owned by Brandon.

**The licence is a placeholder.** `LICENSE` grants nothing today. Contributions are being
accepted under the Developer Certificate of Origin against a repository with no licence,
which is an uncomfortable position to leave a contributor in. The vendored apex-rollup MIT
grant is carved out and unaffected. Plan Decision D-08 recommends Apache-2.0. Owned by
Brandon.

**Attribution will not survive packaging.** A plain `LICENSE` file is not a Salesforce
metadata type, so the vendored library's MIT text will not travel into a package version.
Whoever creates the first Core package version has to carry the notice another way;
`packages/core/vendor/apex-rollup/VENDOR.md` names three ways. Owned by the builder, at first
packaging.

**Nothing is protected on GitHub.** Branch protection and outside collaborator workflow
approval were not on when this report was first written, and nothing in this repository
records them being turned on since. The repository is public and has already drawn drive by
pull requests. Owned by Brandon.

## Install and walk through this iteration

**This cannot be done from an install link, and pretending otherwise would be the most useful
thing to get wrong in this report.** No package version exists, because the namespace is
deliberately deferred and no 2GP version has been created. What follows is a source deploy.

1. Authenticate the Dev Hub and confirm it: `sf org list` shows it with a Dev Hub marker.
   `SF_DEVHUB_AUTH_URL` is already set as a repository secret; nothing in continuous
   integration uses it now that the test org is long lived, and it exists so the org can be
   created and refreshed.
2. Create an org from a shape definition in `config/scratch-defs/`: `platform-only.json`,
   `sales-cloud.json`, `npsp.json`, `person-accounts.json`, or `nonprofit-cloud.json` if your
   Dev Hub is entitled. Use `person-accounts` unless you have a reason not to:
   `scripts/org/create-scratch-org.sh person-accounts dev --days 30 --replace`.
3. Deploy in stages, which is what continuous integration does and is how a failure names
   something: `scripts/org/deploy-packages.sh dev`. It deploys the vendored rollup engine,
   then Core, then Giving. **Expect this to fail at the Core stage today.**
4. Assign the `Nonprofit_Admin` permission set, then the `Nonprofit_Admin_Group` group.
5. Open the Nonprofit Hub. The Setup Assistant opens on step one.
6. Load the sample data from Nonprofit Settings, General, Sample Data. Do this on a contact
   membership org and on a junction membership org: the junction load is the one that writes
   household member records, and it has never run against a real org.
7. Walk the admin guide pages in this order:
   [households](../admin-guide/households.md),
   [household naming](../admin-guide/household-naming.md),
   [nonprofit settings](../admin-guide/nonprofit-settings.md),
   [access](../admin-guide/access.md),
   [automation control](../admin-guide/automation-control.md),
   [error log](../admin-guide/error-log.md),
   [health check](../admin-guide/health-check.md),
   [merge and split](../admin-guide/household-merge-split.md).
   Each has a five minute walkthrough and a "common mistakes" section. The Giving and
   relationship pages belong to the v0.2 and v0.3 walkthroughs.
8. What "right" looks like at each step is written on the page. What to watch for that the
   pages do not say: every household should have a name that is not the literal word
   "Household", every greeting should read as something you would put on an envelope, and the
   Error Log should be empty. An Error Log entry after a clean walkthrough is the most useful
   thing this iteration could hand you.
