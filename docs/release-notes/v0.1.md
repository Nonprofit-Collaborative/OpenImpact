**Apex coverage is not measured, and no Apex test has ever been executed.** Coverage is a
number Salesforce computes while running tests in an org, and there is no org. The 626 Apex
test methods are verified only by an offline compiler that checks syntax, types and unknown
classes. The 90 percent target in plan Section 7.2 is unmet and unmeasured, and that is the
single largest gap in this iteration.

Jest tests do run, on every push. 182 pass.

## Open risks

**Nothing has been deployed.** Every check in this repository is static: formatting, lint,
the namespace and standard object greps, the custom metadata and canonical model checks,
Jest, and an offline Apex compiler. None of them deploy metadata or execute Apex. A
deployment will find things none of them can: unknown fields inside SOQL, validation rules
that fight each other, layout and permission set references that do not resolve, governor
limits under real data volume. Owner action: configure the Dev Hub. Owned by Brandon.

**Two defects reached `main` that only a reviewer caught, not a gate.** Three Automation
Registry records named a field belonging to a different custom metadata type, which would
have refused the entire package deployment; and the household merge destroyed the records
it claimed to merge, invisibly, because the call was not all or nothing and its result was
never read. The first is now gated by `scripts/ci/check-custom-metadata.py`. The second is
the kind of defect no static check will ever catch, which is the argument for the Dev Hub
rather than for another script. Owned by the builder.

**Untested code paths that destroy data.** Household merge, household split, and the sample
data remove action all delete or reparent records, and none has been executed. Do not run
any of them against real data before the Apex tests have run in an org. Owned by Brandon,
as the person who will be tempted.

**The name.** "Open Impact" is in use, including by a foundation doing open source work,
which is close enough to this project to be a real conflict. The name is in the repository
name, the package names, the app name, the label prefixes and the documentation. Renaming
gets more expensive every iteration. Owned by Brandon.

**The licence is a placeholder.** `LICENSE` grants nothing today. Contributions are being
accepted under the Developer Certificate of Origin against a repository with no licence,
which is an uncomfortable position to leave a contributor in. The vendored apex-rollup MIT
grant is carved out and unaffected. Plan Decision D-08 recommends Apache-2.0. Owned by
Brandon.

**Attribution will not survive packaging.** A plain `LICENSE` file is not a Salesforce
metadata type, so the vendored library's MIT text will not travel into a package version.
Whoever creates the first Core package version has to carry the notice another way;
`VENDOR.md` names three. Owned by the builder, at first packaging.

**Nothing is protected on GitHub.** Branch protection and outside collaborator workflow
approval are not on. The repository is public and has already drawn drive by pull requests.
Owned by Brandon.

## Install and walk through this iteration

**This cannot be done yet, and pretending otherwise would be the most useful thing to get
wrong in this report.** No package version exists, because the namespace is deliberately
deferred and no 2GP version has been created. There is no install link.

What is possible today, once a Dev Hub exists:

1. Authenticate a Dev Hub and set `SF_DEVHUB_AUTH_URL` in the repository secrets.
2. Create a scratch org from each shape definition in `config/scratch-defs/`:
   `platform-only.json`, `sales-cloud.json`, `npsp.json`, `person-accounts.json`.
3. `sf project deploy start` for `packages/core`, then `packages/giving`. Deployment order
   matters: Giving depends on Core.
4. Assign the `Nonprofit_Admin` permission set, then the `Nonprofit_Admin_Group` group.
5. Open the Nonprofit Hub. The Setup Assistant opens on step one.
6. Load the sample data from Nonprofit Settings, General, Sample Data. Do this on a
   contact membership org and on a junction membership org: the junction load is the one
   that writes household member records, and it has never run against a real org.
7. Walk the admin guide pages in this order:
   [households](../admin-guide/households.md),
   [household naming](../admin-guide/household-naming.md),
   [nonprofit settings](../admin-guide/nonprofit-settings.md),
   [access](../admin-guide/access.md),
   [automation control](../admin-guide/automation-control.md),
   [error log](../admin-guide/error-log.md),
   [health check](../admin-guide/health-check.md),
   [merge and split](../admin-guide/household-merge-split.md),
   [gifts](../admin-guide/gifts.md),
   [quick gift entry](../admin-guide/quick-gift-entry.md).
   Each has a five minute walkthrough and a "common mistakes" section.
8. What "right" looks like at each step is written on the page. What to watch for that the
   pages do not say: every household should have a name that is not the literal word
   "Household", every greeting should read as something you would put on an envelope, and
   the Error Log should be empty. An Error Log entry after a clean walkthrough is the most
   useful thing this iteration could hand you.
