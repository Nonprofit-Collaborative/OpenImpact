# v0.4 draft release notes: Receipts and year end statements (G-13, ADR-0016)

Written for Maria, to be folded into `v0.4.md` at the end of the iteration (plan Sections 7.4
and 7.5).

- **Open Impact now produces the receipt a donor needs at tax time.** One numbered PDF for one
  gift, from a button on the gift, and one consolidated statement per donor for a whole year,
  from a batch you start in Nonprofit Settings. The file is stored on the receipt, and on the
  gift for a single gift receipt, so anyone who works with giving can open the exact copy the
  donor received. It is deliberately not stored on the donor's own record: see
  [Who can read a receipt](v0.4-draft-receipt-file-access.md).
- **A receipt number is used once and never again.** Numbers read as prefix, year, counter
  (`HFH-2026-000001`). You set the prefix and the starting counter in **Nonprofit Settings,
  Receipts**, before you issue anything.
- **Gaps in the numbering are expected, and every one of them is explained.** If a document
  fails to generate after its number was handed out, that number is not given to anybody else.
  Open Impact writes a receipt record with status Void and the reason "Generation failed", so
  an auditor asking what happened to number 47 gets an answer rather than silence.
- **A receipt never changes once it is issued.** To correct one you void it and reissue it:
  the void records why and when, **the file the donor already has is left completely alone**,
  and the replacement takes the next number. The two records point at each other, so from
  either document you can find the other.
- **Nobody can edit or delete an issued receipt or its file**, including Nonprofit Admin. There
  is no switch for this. Issuing, voiding and reissuing are actions Open Impact performs on
  request; they are not write access to the record.
- **The tax wording is written by Open Impact, not by you, and you cannot delete it.** Whatever
  your letter says, every document carries what IRS Publication 1771 requires: the no goods or
  services sentence; for a gift where the donor received something, the description, your good
  faith estimate of its value, and the deductible amount; and the intangible religious benefits
  sentence where that applies. You write the letter around those sentences, with merge tokens.
- **A gift of goods is described and never valued.** An in-kind receipt prints the description
  the donor gave and no value at all, because valuing donated property is the donor's
  responsibility. The Fair Market Value you record stays in Open Impact for your reporting.
- **A year end statement states the status of every gift on that gift's own line**, so a
  refunded gift in a year's list is visible where a reader is looking, not in a footnote.
- **A statement run is resumable.** A donor who already holds a statement for the year is
  skipped, so running the batch again after a failure finishes the job rather than sending
  anybody a second document. Each run has a record with counts, and a chunk that fails is
  counted and logged and never stops the rest of the org being receipted.
- **Three new things to look at:** the **Receipts** tab, the **Receipt Runs** tab, and the
  **Receipts** panel in Nonprofit Settings.
- **Gifts gain three fields** for the quid pro quo disclosure: what the donor received, your
  good faith estimate of its value, and a checkbox for intangible religious benefits. The
  deductible amount is calculated on the receipt rather than stored, so there is only one place
  for it to be right.

## Two things this release does not settle

Both are recorded in ADR-0016 as spikes that need a real Salesforce org. **No Apex in this
repository has ever been executed and no org was available while this was built**, so neither
has been run. Both are written up here rather than left to be discovered.

1. **Whether `Blob.toPdf()` is metered as a callout inside a batch.** If it is, a batch chunk
   would be capped at ten documents and a large year end run would be far slower than the design
   assumes. The fallback ADR-0016 names, a Visualforce page rendered as PDF, remains available:
   generation sits behind the `ReceiptRenderer` interface and the implementation is chosen by a
   setting, so moving to it is a class and a settings value, not a rebuild.
2. **How the logo and the signature image reach the renderer.** Three routes are named in
   ADR-0016 and none has been tried. **A receipt with no logo and no signature is a legally
   valid receipt**, so this blocks nothing, but until it is settled those images may not appear
   on the PDF. The admin guide says so on the page, so an administrator whose logo does not
   print knows it is this and not their setup.

The v0.4 performance baseline also has to measure a large run: 40,000 households at the shipped
chunk size of 25 is 1,600 chunks, and the chunk size is a starting point to be measured rather
than a settled number.
