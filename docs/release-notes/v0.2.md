# v0.2: giving core, the rollup engine, and importing without a consultant

**Date:** 2026-09-08
**Packages changed:**

- Open Impact Core, no package version created (namespace deferred, plan Section 4.3)
- Open Impact Giving, no package version created

This is the internal iteration report. The admin-facing lines are collected in
`v0.2-draft-setup-assistant.md`, `v0.2-draft-rollups.md`, `v0.2-draft-import.md`,
`v0.2-draft-giving-objects.md` and `v0.2-draft-gift-entry-dashboard.md`, and are assembled
into the public release notes when a version is promoted.

Read the two honesty sections first: **Org shapes passing** and **Open risks**. Every Apex
test written in this iteration is unexecuted, and the iteration shipped a defect that made
donor totals negative before another feature found it.

**This iteration did not follow the plan's sequencing, on purpose.** Plan Section 6 says not
to start an iteration's features until the previous iteration's package version is promoted
and installed. No package version exists, the namespace is deferred, and the owner directed
the build session to run features from several iterations at once (plan Section 9.6). Most of
v0.2 was therefore built in parallel with v0.1 rather than after it. C-12 is the clearest
case: the plan asked for a skeleton in v0.1 and the full version in v0.2, and the full
version was built directly, so v0.1 never had a skeleton to review. What still held is the
per feature discipline: canonical model first, one branch per feature, review against plan
Sections 7.4 and 9.4, squash merge.

## Open risks

**The refund defect, fixed, and worth reading even so.** Every packaged rollup sourced from
Gift filtered on `Status equals Received`. A refund is a new gift for a negative amount whose
own status is Received, and the package writes Refunded onto the original (R-G3). Those two
do not compose. A gift of 250 refunded in two parts of 100 and 150 left the +250 outside the
filter and both negative rows inside it, so the sum was **-250, not 0**: the refund subtracted
the gift a second time. It reached Total Giving, all three fiscal year totals, Fund and Appeal
Total Raised, Commitment Paid To Date and Installment Paid Amount, the five aggregate reports
behind the Giving Overview dashboard, and the sentence in the Gift Status field help and the
dashboard guide saying only Received gifts count.

ADR-0022 fixes it in the filter rather than in R-G3. Money rows now filter on the status set
Received, Refunded, Written off: a partial refund of 100 against 250 nets to **150**, a full
refund nets to **0**, a write off nets to **0**, and a Pending or Failed gift is still
excluded. Count rows, largest gift and the two date rows take that same set plus `Amount
greater than 0`, so a donor who gave 250 and had all of it back reads **one gift and a total
of zero**. 38 of the 41 shipped rollup records carry the status set and 18 of them carry the
positive amount condition; the three pledge balance rows filter on commitment status and were
correctly left alone. The five aggregate reports take the status set and none takes the amount
condition, because all five sum money and none counts. Recent Gifts was deliberately left
alone: it is a list, it shows the status column, and a refund is exactly the case where the
honest answer is that the gift arrived and then went back.

Two consequences are permanent and are documented rather than hidden. A count and a sum now
answer different questions, so they no longer divide into a meaningful average gift. And a
gift recorded at zero is not counted, which matters for in-kind gifts when they arrive in
v0.4; the fix, if it is wanted, is a one row edit an administrator can make.

The risk this leaves is not the arithmetic. It is that a defect which made a number wrong
rather than making something fail passed review, static analysis and merge, and was caught by
the next feature that read the same filter. No static check will catch the next one. Owned by
the builder.

**Nothing has been deployed, and the first attempt failed with nothing attached to it.**
The Dev Hub gap from v0.1 is resolved: a Dev Hub is connected, a test org secret is set, and
continuous integration deploys the vendored engine, then Core, then Giving in separate stages
and runs the Apex tests. The Core stage fails with an `UNKNOWN_EXCEPTION`, zero components
deployed and zero component errors, which is a Salesforce side failure rather than a named
component error. Staged deployment exists precisely so that failure names a stage instead of
hiding behind all 982 components at once. Until it passes, every claim in this report about
runtime behavior is reasoning rather than observation. Owned by the builder, in progress in a
separate session.

**The rollup engine is vendored, and nobody has watched it run.** ADR-0015's whole argument
is that a proven library beats one written here, and the adapter maps a definition onto it in
memory through the text variants only. That mapping, all three modes, the nightly job, the
freshness stamps and the fiscal year window have never executed. The vendored tree carries
531 test methods of its own, and none of those has run here either. Plan Section 11.1 rates
rollup correctness bugs as very high impact, and this iteration has just demonstrated the
kind of bug it meant. Owned by the builder.

**The import framework writes to real objects and has never run.** Dry run is the mitigation
and it is a good one: it writes nothing and reports counts and reasons. Commit does write, in
chunks, through a batch. Do not point it at real data before the Apex tests have run in an
org. Owned by Brandon, as the person holding the spreadsheet.

**Attribution will not survive packaging.** A plain `LICENSE` file is not a Salesforce
metadata type, so the vendored library's MIT text will not travel into a package version.
This iteration is the one that made the vendored code load bearing: every packaged giving
total now runs through it. Whoever creates the first Core package version has to carry the
notice another way;
`packages/core/vendor/apex-rollup/VENDOR.md` names three ways. Owned by the builder, at first
packaging.

**The `nonprofit-cloud` shape's feature string is unverified.** `NonprofitCloud` in
`config/scratch-defs/nonprofit-cloud.json` is a reasonable guess, not a tested value. An
entitled Dev Hub will either create the org or list the feature names it can grant, and that
list is the answer. Most of what the shape would prove is already covered by Person Accounts;
what genuinely needs it is `OrgShapeDetector` answering "is Nonprofit Cloud installed" against
a real org rather than a stub. Owned by Brandon, who holds the entitlement question.

**The name, the licence and branch protection** are unchanged from `v0.1.md` and still owned
by Brandon. They are not repeated here.

## Install and walk through this iteration

No package version exists, because the namespace is deferred and no 2GP version has been
created. There is no install link. This is a source deploy, and step 3 is expected to fail
today.

1. Authenticate the Dev Hub, and create an org from a shape in `config/scratch-defs/`:
   `scripts/org/create-scratch-org.sh person-accounts dev --days 30 --replace`.
2. Deploy in stages: `scripts/org/deploy-packages.sh dev`, which deploys the vendored rollup
   engine, then Core, then Giving. **Expect the Core stage to fail with an
   `UNKNOWN_EXCEPTION` until the session working on that has finished.**
3. Assign `Nonprofit_Admin` and then `Nonprofit_Admin_Group`, and assign `Giving_Admin` for
   the Fundraising app.
4. Open the Nonprofit Hub. The Setup Assistant opens on step one. Walk it end to end,
   including the module inventory step, and let it record the organization identity the
   receipts will later use.
5. Load the sample data from Nonprofit Settings, General, Sample Data.
6. Walk the admin guide pages in this order:
   [setup assistant](../admin-guide/setup-assistant.md),
   [rollups](../admin-guide/rollups.md),
   [importing](../admin-guide/importing.md),
   [gifts](../admin-guide/gifts.md),
   [funds](../admin-guide/funds.md),
   [appeals](../admin-guide/appeals.md),
   [refunds](../admin-guide/refunds.md),
   [quick gift entry](../admin-guide/quick-gift-entry.md),
   [giving dashboard](../admin-guide/giving-dashboard.md).
   Each has a five minute walkthrough and a "common mistakes" section.
7. What to check that the pages do not say, in this order of usefulness:
   - Enter a gift of 250, refund 100 of it, and read the donor's Total Giving. It must be
     150. Refund the remaining 150 and read it again: it must be 0, the gift count must be
     1, and the Giving Overview dashboard must agree with both. That is the defect this
     iteration shipped and fixed, and it is the single most valuable thing to verify.
   - Import a small CSV as a dry run first. The counts it predicts and the counts the commit
     reports must match.
   - Open the Rollups page and press Recalculate all, then check that every "last calculated"
     stamp moves.
   - The Error Log should be empty. An entry after a clean walkthrough is the most useful
     thing this iteration could hand you.
