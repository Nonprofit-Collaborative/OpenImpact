# v0.4 draft release notes: settings stopped refusing values they should accept (C-03)

Written for Maria, to be folded into `v0.4.md` at the end of the iteration (plan Sections
7.4 and 7.5). These are the settings fixes from the first Apex test run this project has ever
had in a real org.

- **The Setup Assistant works again.** Marking a step done, skipping one, choosing a
  coexistence mode, saving your organization's identity, and setting the fund defaults all
  failed with "One of the values is not in the format this setting expects, so nothing was
  saved." The assistant records the time you started setup, and the settings service turned
  that time into text before reading it back in a format it does not accept, so it refused
  the package's own write. Every write path in the assistant records the start time first, so
  every one of them failed, on the first click, in every org.
- **A setting can now be saved with a value of any type, not only text.** Anything the
  package hands the settings service in its own Apex type, a date and time most of all, is
  stored as it is (canonical model R-S5).
- **The settings history no longer claims a setting was empty when it had never been set.**
  A change to a setting nobody had ever set now records no old value at all, which is what
  the record could actually say back (canonical model R-S4).
- **Receipts is a section the rest of the app knows about.** The Receipts panel Giving ships
  was in a section name Core had never been told, so no setup step could send anybody to it.
  The admin guide's list of sections now names it too.
