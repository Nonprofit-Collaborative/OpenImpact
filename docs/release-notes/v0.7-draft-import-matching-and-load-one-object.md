# v0.7 draft release notes: import matching and load one object

Draft lines for the v0.7 release notes, written for Maria (plan Section 7.5). Features C-32 and
C-33, in Core. Admin guide: [Importing](../admin-guide/importing.md).

## Import matching and per-file values (C-32)

- **Organizations have their own matching rule.** Match them by exact name, as before, or by an
  identifier from your other system in a field you pick.
- **Pick the identifier field.** The External ID rule for people, and the new one for
  organizations, match on a field you choose from your org's external ID and unique fields.
- **A row that finds more than one record is rejected by default.** Two contacts with one
  email, or two organizations with one name, no longer quietly resolve to the oldest record.
  You can choose to use the most recently changed one instead, and the dry run lists every such
  row either way. Mappings saved before this release reject such rows too.
- **Values for every row of a file.** Give a value that applies to the whole file, such as the
  appeal every gift in it answers, without adding a column to the spreadsheet.
- **Affiliations load with the people.** Map a role, start date or primary flag and each row
  connects its person to its organization, updating a current affiliation rather than adding a
  second. Undo removes the affiliations an import made.
- **Imports no longer fill your data storage.** When a commit finishes, the copy of your file's
  rows is deleted, except the rejected rows, which stay for the undo window.
- **Checkbox columns understand more words.** y, x, checked, on and t now tick a box and n, off
  and f untick it. A value BarnCRM cannot read is left out and named in the run log, instead of
  unticking the box.

## Load one object (C-33)

- **Load the records of any one object.** A mapping can load a single object instead of
  people: volunteer hours, program enrollments, an export you fixed in Excel, or an object your
  organization built itself.
- **Insert, update or upsert.** Create every row, update records by their Id, or match on an
  external ID field and create the ones nobody has. Each choice says what it risks.
- **Lookups by the field you have.** A column naming another record finds it by Id, by an
  external ID or unique field, or by name. A lookup that finds nobody, or more than one record,
  rejects the row by default, and the dry run lists it.
- **The same safety as every import.** Dry run, control totals, the journal and undo work the
  same way, everything runs with your own access, and the fields BarnCRM or Salesforce keep
  themselves (rollup totals, household names and greetings, formulas) are never imported over.
