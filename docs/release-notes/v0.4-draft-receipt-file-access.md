# v0.4 draft release notes: Who can read a receipt, and where the letters come from (G-13, ADR-0034)

Written for Maria, to be folded into `v0.4.md` at the end of the iteration (plan Sections 7.4
and 7.5). Three defects a security review found in receipting, all fixed together because they
are the same object graph.

- **A receipt PDF is now readable only by people who work with giving.** The file is attached to
  the **Receipt** record, and for a single gift receipt to the **Gift**, and it is no longer
  attached to the donor's household or contact record. Before this change, anybody who could read
  a contact could open that donor's year-end statement from the Files list: their whole giving
  history for the year, your tax identification number, and the name of whoever signs your
  letters. Program staff and volunteer coordinators hold a Core role and no Giving permission set,
  so that was most of the people in a typical org.
- **To find a donor's documents, open the donor, then the Receipts related list, then the
  receipt.** This is one click further than it used to be, and it is the click that makes reading
  a tax document take a Giving permission set. The Access page and the Receipts page both say so
  now, in a table, so nobody has to guess.
- **If you have already issued receipts, the old files keep their old attachments.** Open Impact
  does not remove a file attachment it cannot tell apart from one somebody made on purpose. If
  your org issued receipts before installing this version, remove the receipt files from the donor
  records once, by hand, from the Files list on each donor. Everything issued from now on is
  attached correctly.
- **The Receipts page no longer fails on a brand new org.** The two shipped letters are created
  when the Giving package is installed, along with the giving totals, rather than the first time
  somebody opens the page. Opening that page on an org that had never issued a receipt used to
  show an error instead of the letters.
- **If the letters are missing, there is a button.** The **Restore the shipped letters** button on
  the Receipt templates tab brings back anything the install did not create. It never touches a
  letter you have edited, and pressing it twice changes nothing the second time.
- **Editing a receipt letter now needs the Nonprofit Admin role.** Saving a letter, switching one
  on, and restoring the shipped letters all need the Manage Nonprofit Settings permission, which
  is what every other page in Nonprofit Settings already required. Issuing, voiding and reissuing
  receipts are unchanged: those still need only Giving Staff, because they are day to day work
  rather than configuration. If you hold Giving Admin and not Nonprofit Admin, ask for the
  Nonprofit Admin role and the page tells you so.

## What still needs a real org

**No Apex in this repository has ever been executed, and no org was available while this was
built.** The attachments a receipt file carries are asserted exactly by the tests and can be
checked offline. What the platform then does with those attachments cannot be, so one check joins
the v0.4 walkthrough: sign in as somebody holding a Core role only, with no Giving permission set,
open a donor who has a year-end statement, and confirm the Files list has no receipts in it.

Read [Receipts and year-end statements](../admin-guide/receipts.md) and
[Access](../admin-guide/access.md).
