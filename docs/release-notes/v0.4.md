## Features completed against the plan

| ID | Feature | Package | Notes |
|---|---|---|---|
| G-12 | Acknowledgment rules and templates with sent tracking | Giving | Rules match a gift and name a standard `EmailTemplate`, which the platform sends, so the package composes no HTML and merges no tokens. The trigger sets a gift's acknowledgment status and sends nothing, because a trigger that sent mail would fire two hundred emails inside an import. Sent tracking is a record rather than a field, so "which letter did they get" and "did it go twice" both have answers. The guard against thanking twice is a unique key claimed before anything is sent, so a retried chunk resumes rather than duplicates. The letter path produces a merge file rather than calling `ReceiptWriter`: ADR-0032 explains what is deliberately not shared with receipts. Merged at 11:17 today, after this audit began. |
| G-13 | Receipts: numbered immutable PDF per gift, consolidated year-end statements, batch generation | Giving | Four objects (Receipt, Receipt Number Sequence, Receipt Run, Receipt Template). Numbering is a locked sequence row per series with block allocation; a consumed number with no surviving receipt is written as a Void receipt with reason "Generation failed", so a gap always has an explanation. Void and reissue ship with the feature, and voiding never touches the stored file. IRS Publication 1771 language is code rather than editable prose, and the branch went stricter than ADR-0016 by disclosing whenever a benefit is recorded rather than only above 75 dollars. **Two things are not right yet:** the Receipts settings panel named a Giving component in a Core-only mechanism and rendered as "not installed" for every administrator from the moment it shipped until commit `702362d` today, and the `receiptActions` component that carries the Issue receipt button is still on no page. Both are under Open risks. Both ADR-0016 spikes are unrun. |
| G-14 | Donor levels (configurable tiers, auto-assign, previous level, movement) | Giving | A level is a label on a rollup total that already exists on the same record, so a level can never disagree with the number printed beside it (ADR-0028). Which total the ladder measures is a setting: total giving, this fiscal year, last fiscal year, or largest gift. Previous level and changed date are kept, so movement is a list view. A refund moves a donor down, because the level states what the current total earns. Placed on save, re-placed nightly, and a Recalculate now button. Open Impact ships no levels of its own, so the ladder is empty until the organization builds it, which is deliberate and is also why the sample data has no levels in it. |
| G-16 | Retention reports: LYBUNT, SYBUNT, new versus retained, first-to-second conversion | Giving | Four reports in the Open Impact Giving folder, plus one report type (Donors with Giving) whose rows are donors rather than gifts. The definitions were written first, in ADR-0026, and the admin guide states each one in Maria's language. One new attribute, `Gifts_Last_Year__c` on Account and Contact, filled by three new shipped rollup defaults, because a sum could not answer the retained question honestly: a gift refunded inside last year sums to zero and its donor would have read as reactivated. The reports read the fiscal year in Setup while the rollups read the one in Nonprofit Settings, which is why ADR-0025 exists and why C-11 added a finding that compares them. |
| G-18 | In-kind gifts with fair market value and description | Giving | In-kind is a gift type carrying no amount, so it adds nothing to total giving, gift count, fund or appeal totals, the dashboard, or a donor level (ADR-0030). Two separate totals, In-kind value and In-kind gift count, on household, organization and person. The receipt for goods describes and never values. Five validation rules refuse the mistakes that matter, including a cash gift left carrying an in-kind value after a type change. Quick Gift Entry swaps the amount box for description and value. One new report. This is the only feature of the iteration that extended the sample data, which now carries 23 in-kind gifts. |
| C-18 | Seasonal address swap job with visible last run | Core | The address a season replaced is marked, so the spring swap puts back exactly what it took out rather than working it out again. A range crossing New Year is one season. Last run time and a one-sentence summary appear on the Hub home and on the Addresses page of Nonprofit Settings, with a "not run in 36 hours" warning when the job is scheduled. Scheduling, unscheduling and Run the swap now are all in the app. Two seasonal addresses covering the same day are reported rather than picked silently, and the first one added wins. Runs in system mode under ADR-0027. |
| C-10 | Sample data extended to Giving | Core and Giving | 709 gifts across three years, 8 funds, 7 appeals, 24 commitments with installments, 30 soft credits and 24 tributes, dated relative to the load so "this year" is never empty. Two refunded gifts and one written off, and one monthly donor three payments in arrears. A module contributes its own sample data through `SampleDataModule` without Core knowing about it. Remove Sample Data removes all of it. Closes the gap `v0.2.md` recorded, where the Giving walkthroughs had nothing to open. |
| C-11 | Three new Health Check findings | Core | Whether anyone still holds Override Receipt Lock, and who; whether the two fiscal years disagree; and how many receipts failed to generate. All three work on a Platform-only org with no Giving installed, through a describe and a dynamic query, so ADR-0009 and ADR-0013 hold. The first is the finding ADR-0024 deferred: a permission meant to be granted for one correction and taken away again is exactly the thing nothing else would ever mention again. |
| C-13 | Shipped rollups created at install | Core and Giving | A defect fix, not new work: the shipped rollup definitions were created only by a button nothing told an administrator to press, so a fresh install had every giving total blank. Each package's post-install script now creates its own (ADR-0029), matched by definition key so an upgrade adds what is new and changes nothing an administrator edited. Nothing throws: a failed bootstrap writes to the Error Log rather than aborting an install. The source deploy script runs the same work as anonymous Apex, because a source deploy runs no post-install script. |
| G-10 | A refund reverses the matched donor credit | Giving | Closes the one open defect `v0.3.md` left standing. A refund of the employer's gift now writes a negative matched donor credit for the employee, so a partial refund leaves partial recognition and a full refund leaves zero, with both rows visible rather than either erased (ADR-0031). The old guidance to unlink the pair before refunding is withdrawn, and ADR-0023's incorrect reference to G-09 was corrected to G-10 in the same change. |

Two more changes landed in this window and belong to earlier iterations, recorded here because
they are on `main` and change what those features do:

- **G-04, the receipt lock** (ADR-0024): a gift carrying a receipt number refuses changes to
  amount, date, donor and in-kind description, and the lock survives the automation switch,
  because a lock an administrator can turn off is not a lock. Lifting it is a deliberate act in
  Setup, granting Override Receipt Lock, which is the Setup step C-11's new finding then reports
  on. This is a deliberate exception to plan Section 7.4's "no Setup step required for normal
  use": voiding a receipt is not normal use.
- **Five tests that passed without testing what they claimed** were fixed after an audit of all
  782 Apex test methods then on `main`. The sharpest deleted a gift and asserted its soft credits
  were gone, which a master-detail cascade guaranteed regardless of whether the code under test
  existed at all.

## Open risks

**`main` is red, and it is red the same way every time.** The `org-tests` job on the two most
recent pushes to `main` (runs 88 and 94, commits `7c88965` and `03d3b9b`) both failed at the
"Deploy the packages, in stages" step, and both skipped the Apex tests as a result. The failure is
exact and worth quoting: stage Core, `UNKNOWN_EXCEPTION: An unexpected error occurred. Please
include this ErrorId if you contact support: 399691152-105965 (-315522575)`, with
`numberComponentsDeployed: 0`, `numberComponentErrors: 0`, `numberComponentsTotal: 903`, 644 files,
a 2,647,737 byte payload, and an empty `componentFailures` array. `docs/contributor-guide/ci.md`
records four earlier failures with the same trailing ErrorId code, `-315522575`, behind a different
leading number each time. That is six identical failures now, which is a deterministic fault and
not a flake, and the deploy script's own output still prints the line saying a re-run is worth one
attempt. **Nothing has ever been deployed by this project's continuous integration.** The next
action is a Salesforce support ticket quoting an ErrorId, not another commit. Owned by Brandon,
because it needs a support case against an org he owns; the builder can do nothing more with it.

**A whole panel of the iteration's largest feature was unreachable, and no gate saw it.** G-13's
Receipts settings row named a Giving component in the switch statement that only Core components
can appear in, which ADR-0020 states plainly in its own decision text. Every administrator opening
Nonprofit Settings, Receipts would have seen the words "not installed" where the panel that writes
the letters donors read was supposed to be, from `ba7b55a` until `702362d` today. It was found by a
sibling session building G-12, which used the navigation form and so did not hit it, and the check
that should have caught it now scans every package rather than only Core. The lesson is the one
that keeps repeating in these reports: it was found by a neighboring feature, not by a gate, and
the gate was written afterwards. Owned by the builder, fixed.

**Its twin is still open. The Issue receipt button is on no page.** `receiptActions` declares a
Gift record page target, and the shipped `Gift_Record_Page` flexipage carries `giftSoftCredits` and
`tributeNotification` and nothing else. No quick action names it either, where `giftRefund` and
`householdMergeSplit` at least have one. So step 3 of the receipts walkthrough, "Open any gift from
the sample data. Click Issue receipt", cannot be performed on the page this project ships, and the
admin guide never tells the reader to add the component by hand. Two older components,
`commitmentSchedulePreview` and `receiptActions`, are in the same state. **There is still no check
that an exposed component is reachable from anywhere**, which is the gate this iteration should have
produced and did not. Owned by the builder, and it is a small fix and a real one: without it, a
correct receipting feature cannot be operated. Do not close G-13 until this is done.

**Neither of ADR-0016's spikes has been run, and the named fallback does not exist as code.**
Whether `Blob.toPdf()` is metered as a callout inside a batch decides whether a year end run for a
large organization is feasible or is 1,600 chunks of ten documents each. How a logo and a signature
image reach the renderer has never been tried, and a receipt with neither is still a legally valid
receipt, which is why this blocks nothing. The release note says moving to the fallback is "a class
and a settings value, not a rebuild", and the setting genuinely exists and genuinely takes a class
name: **but the Visualforce fallback class is not in the repository, and there is no Visualforce
page anywhere in it.** Somebody has to write it first. Owned by the builder, at the first org that
will run a batch.

**The Platform-only shape has never been created, in four iterations.** ADR-0013 requires Core to
run on it, the first customer who has neither Sales Cloud nor Person Accounts is the one who finds
out, and the only enforcement is a grep over source text. This iteration made it worse in one
specific way and better in another: C-11's three new findings read the platform's own setup objects
and describe Giving's objects dynamically precisely so they keep working on a Platform-only org,
which is careful work that nobody can confirm, and the test org is now known to have both Sales
Cloud and Person Accounts, so it would hide exactly the mistake ADR-0013 exists to prevent. Testing
it costs a second org and a second secret. Owned by Brandon, since it is an org and a secret.

**Three features ship an object with no sample data behind it.** Receipts, donor levels and
acknowledgment rules all start empty in a freshly loaded demo org. For receipts and donor levels
that is a stated decision with a good reason behind each (a receipted gift cannot be deleted, and
level amounts belong to the organization). For G-12 no reason is recorded. The practical effect is
that three of this iteration's walkthroughs begin by creating data rather than by opening something,
which is slower to demonstrate and easier to get wrong. Owned by the builder.

**The numbers this iteration added are the kind that are wrong quietly.** Donor levels, in-kind
totals, `Gifts_Last_Year__c` and four retention reports all produce a figure that looks plausible
whatever it says. No rollup was recalculated in an org, no report was opened, and the retention
definitions in ADR-0026 have been checked against the report filters by reading them side by side
and in no other way. The mitigation in the admin guide is the right one and should be followed:
spot check one donor from each list against their gift history before the first mailing. Owned by
Brandon at first use.

**A donor's totals and the retention reports read two different fiscal years.** Salesforce reports
read the fiscal year in Setup; the rollups read Fiscal Year Start Month in Nonprofit Settings. When
they disagree nothing errors, and the reports simply disagree with the donor record until somebody
questions a year end number. C-11's new Health Check finding names both months and links to the
setting, which is the right mitigation and is not the same as the problem being gone. Owned by
Brandon, as a setup step, and it is the first step on the retention reports page for that reason.

**The new tabs are in no app.** Receipts, Receipt Runs, Acknowledgments, Donor Levels as a page,
and also Commitments, Soft Credits and Tributes from v0.3, all exist as tabs and none of them
appears in the Fundraising app's tab list, which holds Quick Gift Entry, Gifts, Funds, Appeals,
Donor Levels as an object tab, and the standard report and dashboard tabs. They are reachable
through the App Launcher, so this is friction rather than breakage, and the settings console
navigation rows reach their pages regardless. It is still not what the release notes describe when
they say "three new things to look at". Owned by the builder.

**G-13 opens a seam through the lock G-04 closed hours earlier.** `allowReceiptNumberChange` is a
private `@TestVisible` static that only `GiftService` can flip, `recordReceiptNumbers` is public but
not `NamespaceAccessible`, the seam lifts only the receipt number branch and never amount, date or
donor, and it is restored in a `finally`. A bare void deliberately leaves the gift locked. That
reasoning is recorded in the merge commit and reads as sound, and it has never executed. A door
through ADR-0024 is the thing to re-read first when the tests finally run. Owned by the builder.

**Nothing on GitHub is protected**, unchanged since `v0.1.md` and still unrecorded as done.
Meanwhile every feature in this iteration was pushed straight to `main`, and this report was
written while two more commits landed underneath it. Owned by Brandon.

**The name and the licence** are unchanged from `v0.1.md` and still Brandon's. `LICENSE` still
opens with "License: to be confirmed by the project owner" and still grants nothing, while
contributions continue to be taken under a DCO against a repository with no licence. Renaming and
relicensing both get more expensive every iteration, and this iteration added four objects, thirty

## Install and walk through this iteration

No package version exists, because the namespace is deferred and no 2GP version has been created.
There is no install link. This is a source deploy, and **step 2 is expected to fail** on the Core
stage with the `UNKNOWN_EXCEPTION` above until the Salesforce support case is answered. Everything
after step 2 is written for the day it passes.

1. Create an org from the Person Accounts shape, which is the shape the test org already is:
   `scripts/org/create-scratch-org.sh person-accounts dev --days 30 --replace`.
2. Deploy in stages: `scripts/org/deploy-packages.sh dev`. **Expect the Core stage to fail.** The
   script runs `RollupService.ensureDefaults()` as anonymous Apex after the last stage, because a
   source deploy runs no post-install script and would otherwise leave the org without the rollup
   definitions C-13 now creates at install.
3. Assign `Nonprofit_Admin`, then `Nonprofit_Admin_Group`, then `Giving_Admin`.
4. Open the Nonprofit Hub, walk the Setup Assistant, and set the coexistence mode to Agentforce
   Nonprofit.
5. Load the sample data from Nonprofit Settings, General, Sample Data. Then open the Rollups page
   and choose Recalculate: giving totals are computed by the rollup run, not as each gift is saved,
   and the dashboard and the donor levels are blank until it finishes.
6. **Before walking the receipts page, put the `receiptActions` component on the Gift record page in
   the Lightning App Builder.** It is not there, and the walkthrough's Issue receipt button is on
   it. This is the open defect above, and needing this step is the confirmation of it.
7. Walk the admin guide pages in this order:
   [receipts](../admin-guide/receipts.md),
   [in-kind gifts](../admin-guide/in-kind-gifts.md),
   [donor levels](../admin-guide/donor-levels.md),
   [retention reports](../admin-guide/retention-reports.md),
   [acknowledgments](../admin-guide/acknowledgments.md),
   [addresses](../admin-guide/addresses.md) (the second walkthrough, the seasonal swap),
   [rollups](../admin-guide/rollups.md),
   [health check](../admin-guide/health-check.md).
8. What to check that the pages do not say, in this order of usefulness:
   - Set the fiscal year in Setup and Fiscal Year Start Month in Nonprofit Settings to the same
     month **before** anything else, then recalculate. Health Check will tell you if you did not.
     Every number below depends on it.
   - Issue a receipt, then try to change the gift's amount. The save must be refused. Then void and
     reissue, and confirm the original PDF is still there, unchanged, alongside the new one. If
     `Blob.toPdf()` throws inside the batch, that is ADR-0016's first spike answering itself, and it
     is the single most valuable thing this walkthrough can tell you.
   - Look at whether the logo and the signature appear on the PDF at all. Nobody knows.
   - Run the year end statement batch twice. The second run must skip every donor who already holds
     a statement rather than sending a second document.
   - Enter an in-kind gift with an amount typed into it. It must be refused. Then confirm total
     giving did not move and In-kind value did, on the same record.
   - Refund an employer's matching gift and check the employee's recognition drops by the refunded
     amount, with two visible rows rather than one erased one. That is the v0.3 defect this
     iteration closed.
   - Open all four retention reports and spot check one donor in each against their gift history.
     A donor whose last year gift you refunded this year should still be on LYBUNT; a donor whose
     gift you refunded this year should not be.
   - Give the Garcia household a seasonal address covering today, choose Run the swap now, and
     confirm the last run line reads "1 moved to a seasonal address, 0 moved back, 0 could not be
     changed" and that the household's standard address boxes read Phoenix.
   - The Error Log should be empty. An entry after a clean walkthrough is the most useful thing this
     iteration could hand you.
