# v0.3 draft release notes: The receipt lock survives the automation switch (G-04, ADR-0024)

Written for Maria, to be folded into `v0.3.md` at the end of the iteration (plan Sections
7.4 and 7.5).

- **A receipted gift is locked, and nothing on the Automation page unlocks it.** Once a gift
  carries a receipt number, its amount, date, donor and receipt number cannot change and the
  gift cannot be deleted. That rule now runs from its own automation, **Gift: receipt lock**,
  which no switch turns off.
- **Pausing all automation no longer suspends it.** The pause stops Open Impact filling
  things in for you: households, dates, default allocations. It never stops Open Impact
  refusing something. If you paused automation before a bulk edit expecting receipted gifts
  to become editable, they will not.
- **The Automation page still lists it, and says why it will not move.** The receipt lock
  appears in the list like everything else, with its switch off, greyed out, and a line
  reading "This automation enforces a rule, so it always runs. It cannot be switched off here
  and a pause does not suspend it." You will find it where you went looking for it.
- **There is one way past the lock, and it lives in Setup.** A custom permission, **Override
  Receipt Lock**, ships assigned to nobody: it is on no permission set and in no permission
  set group, so no role carries it, including Nonprofit Admin. An administrator creates a
  permission set for it in Setup, assigns it for the length of one correction, and removes it
  again. The procedure is on the [Gifts page](../admin-guide/gifts.md), under "Lifting the
  receipt lock".
- **Every override is written to the Error Log.** Whenever the lock is lifted, Open Impact
  records an entry at Warning severity naming the gift, its receipt number, and exactly which
  values changed, or that the gift was deleted. Nobody has to remember to write it down.
  Filter the Error Log on Severity `Warning` to see every override an org has made.
- **For builders: `Always_Runs__c`.** Both `Automation_Registry__mdt` and
  `Automation_Setting__c` gain the flag. An automation that enforces a rule rather than
  providing a convenience carries it, the trigger dispatcher skips the bypass, the pause and
  the switch for it, and `AutomationControl.setEnabled` refuses to change it. It is a
  statement the package makes about its own rules: a subscriber cannot set it.

Read [Automation control](../admin-guide/automation-control.md), section "Automations that
always run", and [Gifts](../admin-guide/gifts.md), section "Lifting the receipt lock".
